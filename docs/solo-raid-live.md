# 솔로레이드 진행 중 시즌 (6시간 자동 수집·예측·웹 → 끝나면 보강)

2026-10-16 사용자와 정한 운영 방식. S42부터 **Claude 예약 작업**이 6시간마다 시즌 전용 세션(Sonnet, 레포를 붙인 세션)을 깨워 받기 → 판독 → 예측 → 커밋·push를 하고,
push가 공개 웹(<https://jgaram.github.io/nikke-soloraid-cutoff/>)을 바로 갱신한다 (docs/publish.md).
처음에는 세션 하나가 `send_later`로 정해진 시점(T = 12·18·24·36·48·72·96)마다 깨는 방식이었다가 같은 날 바꿨다 (사용자 결정).

- **진행 중:** 목적은 진행 중 레이드 예측이다. 6시간 칸마다 수집 → 예측 → 커밋 → 웹.
  **S43부터 웹에 나가는 예측은 M3다** (2026-11-07 사용자 결정 — [method 「WP7 정함」](solo-raid-method.md#wp7-정함-2026-11-07-kst--사용자-지시-예측모델-만든거-운영에-적용하자-g6-답)).
  F도 칸마다 함께 내서 커밋한다 (대비·참고, 웹에는 안 나감). M3가 실패하거나 75분을 넘은 칸은 F 한섭 값을 「대체(F)」로 올린다. 웹은 한섭 1·3·10%만.
- **끝난 뒤:** 마지막 수집(종료 후 인증)과 후처리까지는 시즌 전용 세션(Sonnet)이 한다. 이어서 그 세션이 **끝난 뒤 보강 세션(Opus)** 을 새로 열고,
  데이터 점검·예외 처리·자기 예측 채점·수집 끝 표시·분석 갱신·README를 그 세션이 사람 없이 한다 (2026-11-01 사용자 결정 — 아래 「3. 끝난 뒤」).

수집·판독 도구는 [일괄 수집 지시문](solo-raid-backfill.md)의 「시즌 세션 지시문」과 같은 것(`run_window.sh` → `raid-window` Workflow → `merge_obs.py`)을
`tools/solo_raid/live_tick.sh`가 묶어 부른다. 이 문서는 일정·켜기·자동 실행 한 번·끝난 뒤 순서를 정한다.

## 정한 것 (사용자 결정, 2026-10-16)

- **실행 위치:** Claude 예약 작업 하나(「솔로레이드 6시간 자동 수집」)가 **시즌 전용 세션 하나**(레포를 붙여 `create_session`으로 만든 세션)를 칸마다 깨운다.
  GitHub Actions에서는 Haiku 판독을 돌릴 수 없어서다. 처음에는 실행마다 새 세션을 띄웠는데, 예약 작업이 띄운 새 세션에는 레포가 붙지 않았다
  (2026-10-16 점검: 작업 폴더가 비어 있음, Workflow는 있음, `get_trigger`는 없음). 그래서 같은 날 바꿨다.
  세션은 같은 대화로 깨어나지만 컨테이너는 그사이 바뀔 수 있다 — 상태는 언제나 커밋된 `data/solo-raid/S{n}/`에서 잇는다.
  시즌 전용 세션 모델은 **Sonnet** (판독은 `raid-vision` Haiku — Haiku 기반 Workflow라 상시 허락, AGENTS.md). 권한 모드는 auto (점검에서 권한 질문 없음).
- **칸:** 챌린지 시작(`c_start`, 05:00)부터 6시간마다 — 한국 시간 05·11·17·23시가 칸 경계다.
  구간은 **게시 시각으로 경계에서 자른다** (`[지난 성공 끝, 경계)`). 그래서 경계 뒤에 올라온 인증은 늦게 깨어도 이번 칸에 들지 않고 다음 칸으로 간다.
  실행을 경계 15분 뒤로 미루는 안은 자료는 그대로이고 웹만 늦어서 버렸다 (사용자 지적). 예약 작업은 **경계 1분 뒤(05:01·11:01·17:01·23:01)** 에 깬다
  (정각은 예약 작업이 붐비고, 몇 분 일찍 깨도 `live_tick.py`가 같은 칸을 잡고 경계까지 기다린다).
- **예측 시점:** T = 6, 12, 18, …, T_end (종료를 덮는 첫 경계, 대개 120). **매 칸 예측을 내고 웹에 올린다** (T=6부터, 사용자 결정).
  T=6은 % 변환 외삽이라 등급 C 이하로 나온다 (S41 사본으로 확인, 2026-10-16). 웹은 C·D면 가운데 숫자를 흐리게 보인다.
  채점 기준 T(`data/solo-raid/analysis/criteria.json`의 12·18·24·36·48·72·96)는 6시간 칸에 모두 들어 있어 `criteria.json`은 바꾸지 않는다.
  `score_live.py`·`site.py`는 `predict/T*/`를 모두 읽는다 (다른 T도 그대로).
- **예측 기록:** `data/solo-raid/S{n}/predict/T{T}/`(predict_run.sh 출력 그대로)를 커밋한다. 끝난 뒤 정직하게 채점하려는 것이다 (AGENTS.md 「결과물」 예외).
- **기본 도구:** 그때의 `predict_run.sh` 기본(prior·서버 미상 처리)을 그대로 쓴다. 진행 중에 결과를 보고 도구나 설정을 바꾸지 않는다.
  - 예외 (사용자 결정 2026-10-19): 시범 기간이라 **로직에 분명한 잘못이 있으면 고치고 지난 예측에 소급한다.** S42는 T60부터 서버 미상 줄 기본이 mono(점수 비교 거르기, 분석 4.7)이고
    T6~T54도 같은 방법으로 다시 냈다 (예측 JSON `recalc`에 원래 커밋).
  기본을 바꾸는 판정은 분석 문서의 기준(개발 시즌 8개 이상, `criteria.json`)으로만 한다.
  - **S43부터 주 예측 = M3 고정 모델 파일** `data/solo-raid/analysis/model_S{n}_m3.json` (2026-11-07 사용자 결정, `m3_freeze.py`가 만든다 — 사전·꼴·보정 층·고정 코드 커밋을 담는다).
    `live_tick.sh finish`가 F 다음에 `tools/solo_raid/m3_live.py`로 낸다 → `predict/T{T}/m3_T{T}.json`·`.txt`·`m3_run.log`. 칸 하나 보통 5분 안팎, 최악 약 1시간 (4코어, 한도 75분).
    M3는 모델 파일의 `code` 커밋 코드로 돈다 (main의 연구 코드가 바뀌어도 진행 중 예측은 그대로). 시즌 안에서는 모델 파일을 다시 만들지 않는다.
    모델 파일이 없는 시즌은 F만 낸다 (S42까지). 아래 F 설명은 대비로 그대로 돈다.
  - **예측 방법 = 그 시즌의 고정 모델 파일** `data/solo-raid/analysis/model_S{n}.json` (2026-10-18부터, `predict_run.sh` 기본 — 없으면 예측이 멈춘다). S43부터는 F 대비.
    분석 4.3에서 고른 F: 최근 5시즌 prior + 라벨 줄 수준 갱신 + 지난 시즌 오차로 구간 넓히기. 시즌 안에서는 모델 파일을 다시 만들지 않는다.
    S42만 예외로 도중에 바뀌었다 — T6~T24는 S41 한 시즌 prior, T30부터 F (사용자 결정 2026-10-18, [분석 4.5](solo-raid-analysis.md#45-고정과-미래-시험)).
    그 뒤 T6~T24는 10-18 11시 뒤 F로 다시 냈다 (사용자 결정 2026-10-18 — 시점별 예측을 같은 방법으로. T까지 게시된 것만 남긴 사본, 원래 S41 한 시즌 prior 기록은 커밋 `41cb647`·`152c440`·`51edb28`·`1843660`).
    `predict/T{6,12,18,24}/predict_T*.json`의 `recalc`에 방법·원래 커밋·확인(같은 방법으로 T30을 다시 내면 커밋된 T30과 같음)이 있다.
  - **진행 중 예측은 칸마다 그때의 main 도구로 후처리부터 다시 한다** (2026-10-17 레포 정리에서 확인). 그래서 다른 세션이 main에서 후처리 도구·predict 기본값,
    비율을 빌리는 시즌(지금 S41)의 `state/`(prior·core)를 바꾸면 다음 칸 예측이 바뀐다. 진행 중에는 바꾸지 않는다 — 손대지 말 것 목록은 [분석 4.0a](solo-raid-analysis.md#40a-레포-정리-검토-2026-10-17).
- **시작은 사람, 끝은 자동.** 시즌마다 사용자가 「S{n} 자동 수집 켜」라고 한다 (아래 「1. 켜기」). 종료 뒤에는 마지막 수집 한 번으로 스스로 꺼진다.
- **종료 후 수집 끝 `e_end` = 종료 + 4일 05:00** (S42부터, 사용자 결정). 종료가 목요일이면 월요일 05:00이다.
  토요일이 보상 들어오는 날이라 그날과 주말에도 최종 인증이 많이 올라온다 (사용자 설명). S33~S40은 처음에 종료 + 2일 05:00(대개 토요일 05:00, 보상 직전)까지 받았고,
  뒤에 + 4일까지 소급했다 ([소급 표](solo-raid-backfill.md#종료--4일-소급-s40--s32), 10-17 05:42 끝).
  더 길게 받은 S41에서 종료 뒤 % 관측을 12시간 단위로 세면 0–12h 133 · 12–24h 16 · 24–36h 0 · 36–48h 4 · **48–60h(토 05:00~) 34** · 60–72h 13 · 72–96h 10이었다
  (토요일 05:04부터 종료 화면 인증이 다시 몰림, 종료 뒤 관측의 약 27%가 토요일 05:00 뒤).
- **종료 후 수집은 e_end에 한 번** (사용자 결정). 예측·웹에는 영향이 없고 채점·분석용 정답 자료다.
- **모든 새 시즌은 「미래 시험」이다 (사용자 결정, 2026-10-17 — split 판 2).** 끝나면 도구·설정을 고치기 전에, 끝나기 전에 커밋된 예측을
  한 번 채점해 독립 시험 결과로 적고(아래 「3. 끝난 뒤」 4), 그 뒤 개발에 넣는다. 판 1의 시험 몫(S44·S46·S48만)은 쓰지 않는다 (`split.py role`은 모두 dev).
- **예외 처리:** [예외 처리 규칙](solo-raid-backfill.md#예외-처리-규칙)대로 끝난 뒤 점검에서 `S{n}/discard.json`에 남긴다. 자동 실행은 예외를 판단하지 않는다.
- 사이트·UA·작업자·간격은 일괄 수집과 같다 (디시·네이버 게임 라운지·블라블라링크, 자기 이름 UA, 작업자 4·간격 0.5초).

## 일정 예 (S42, KST)

| | 시각 |
|---|---|
| 이벤트 오픈 | 10-15(목) 12:00 (공지 2026-10-05 「10월 8일 업데이트 공지」) |
| 챌린지 시작 `c_start` | 10-17(토) 05:00 (3일차 05:00) |
| 첫 예측 T=6 | 10-17 11:01 실행 → 웹 11:30~11:50쯤 (M3부터는 M3 몇 분~1시간이 더해져 대개 12시 안팎, 늦으면 12:40쯤) |
| 마지막 예측 T=120 | 10-22(목) 05:01 실행 (종료 04:59:59를 덮는 칸) |
| 종료 후 수집 | 10-26(월) 05:01 실행 (`e_end` 05:00) → 예약 작업이 저절로 꺼짐 |

예측 20번 + 종료 후 수집 1번 = 깨우기 21번(+ T=0 칸 05:01의 빈 깨우기 1번). 지난 시즌 2일 구간 기록(새 글 1,100~3,100개, 시트 300~950장)으로 어림하면
6시간 칸 하나는 새 글 150~400개·시트 40~120장, 판독 에이전트 3~10개, 20~40분이다.

## 1. 켜기 (시즌 시작 — 사용자가 「S{n} 자동 수집 켜」라고 할 때)

1. 공식 공지 아카이브 `notices/`에서 이번 솔로 레이드 공지(보스·기간)를 찾는다. 없거나 보스 이름이 없으면 사용자에게 묻는다.
2. `data/solo-raid/S{n}/state/season.json`:
   `name`·`boss`·`start`·`end`, `c_start`(기본 3일차 05:00 — 공지가 다르게 말하면 그것, 근거를 README에), `e_start` = `c_start`, `e_end` = 종료 + 4일 05:00.
   이어서 웹의 보스 그림을 받는다: `python3 -I tools/publish/boss_icons.py` (nikke-analysis에 아직 없으면 「아직 없음」만 나오고 넘어간다 — 웹 빌드가 다음에 다시 시도, [publish 「보스 그림」](publish.md#보스-그림)).
3. `data/solo-raid/S{n}/README.md`를 만든다 (일괄 수집 「시즌 요약」 형식의 머리 + 몫 `python3 -I tools/solo_raid/split.py role S{n}`).
   **맨 끝 절은 「자동 실행」 표로 둔다** — 실행마다 `live_tick.py record`가 README 맨 끝에 줄을 덧붙인다.
4. 시즌 전용 세션과 예약 작업을 만든다 (켜는 세션이 `claude-code-remote` 도구로).
   - `create_session`: `source_url` = `https://github.com/jgaram/nikke-community`, `model` = `claude-sonnet-5-5`, `permission_mode` = `auto`,
     **`environment_id` = 「전체」 환경(네트워크 제한 없음, `list_environments`로 찾는다)** — 빼면 켜는 세션의 환경을 물려받는다. Default는 허용 주소가 없어
     OCR 모델(`huggingface.co`)·수집 사이트가 403으로 막힌다 (S43 T6 실패, 2026-11-14 확인).
     점검에 `curl -sSI https://huggingface.co/ https://gall.dcinside.com/`이 프록시 403 없이 되는지도 넣는다.
     제목 「솔로레이드 S{n} 6시간 자동 수집」, 태그 `solo-raid-live`·`S{n}`. 첫 메시지는 점검으로 한다 —
     레포·main 브랜치, `live_tick.sh plan`, `git push --dry-run origin HEAD:main`, Workflow·`raid-vision`·`PushNotification`·예약 작업 도구가 있는지, 권한 질문이 있었는지.
     `list_events`로 답을 확인한다.
   - `create_trigger`: 이름 「솔로레이드 6시간 자동 수집」, `cron_expression` = `CRON_TZ=Asia/Seoul 1 5,11,17,23 * * *`, `persistent_session_id` = 위 세션,
     `initiation` = human_request, `prompt`는 아래 「예약 작업 프롬프트」 그대로. 이 방식에는 `notifications`를 줄 수 없어 알림은 세션이 `PushNotification`으로 보낸다.
     응답의 `next_run_at`이 다음 칸 1분 뒤인지 확인한다.
   - 지난 시즌 예약 작업이 남아 있으면 `delete_trigger`로 지운다 (전용 세션은 예약 작업이 띄운 세션이 아니라 함께 지워지지 않는다).
5. `data/solo-raid/live.json`: `{"season": "S{n}", "trigger": "trig_…", "session": "session_…", "cron": "…", "model": "…", "on": "켠 KST 시각", "by": "세션 id"}`.
   **M3 모델 파일 `data/solo-raid/analysis/model_S{n}_m3.json`과 F 대비 `model_S{n}.json`이 둘 다 있는지 본다** (S43은 2026-11-07에 만듦 — `m3_freeze.py --season S43`).
   M3 모델 파일이 없으면 그 시즌은 F만 웹에 나간다 — 켜기 전에 사용자에게 알린다. 모델 파일의 `schedule`(H 120 · 05시 시작)이 이번 `season.json`과 다르면 M3가 모든 칸에서 대체(F)가 된다
   (꼴이 05시 시작 120시간 시즌용) — 켜기 전에 사용자에게 알린다.
   F 모델 파일이 없으면 첫 칸 F 예측이 멈춘다. 지난 시즌 채점·수집 끝 뒤 `freeze_model.py`로 만든다
   ([분석 4.5 「S43용 다시 고정」](solo-raid-analysis.md#45-고정과-미래-시험)). 없으면 켜기 전에 사용자에게 알린다.
   **S43은 다시 고정하지 않고 `model_S42.json`을 그대로 옮긴다** (2026-10-20 사용자 결정 — [분석 5.0](solo-raid-analysis.md#50-운영--f-그대로-사용자-결정-2026-10-20), 만드는 법은 [순서표 8](solo-raid-todo.md#8-s43-모델-파일--f-그대로-마지막-s43-c_start-전)).
6. 커밋(`S{n} 자동 수집 켬`) → push. `season.json`이 올라가 웹에 「챌린지 진행 중 · 첫 예측은 6시간 뒤」가 뜬다 (시작 뒤부터).
7. 사용자에게 첫 실행 시각(KST)을 알린다.

### 예약 작업 프롬프트

```
솔로레이드 자동 수집 한 번. docs/solo-raid-live.md의 「2. 자동 실행 한 번」을 처음부터 끝까지 그대로 따른다.
사람이 보고 있지 않으니 묻지 말고, 그 절이 멈추라고 하는 곳에서만 멈춘다. 마지막 답은 그 절의 형식대로 한국어로 쓴다.
이 세션은 6시간마다 같은 대화로 깨어난다. 앞 실행의 기억에 기대지 말고 매번 git pull로 최신 main을 받고 문서를 다시 읽어 판정부터 한다.
```

절차는 이 문서에 두므로, 절차를 바꿀 때 예약 작업은 고치지 않는다.

## 2. 자동 실행 한 번 (예약 작업이 깨운 시즌 전용 세션이 따른다)

규칙: 사람이 보고 있지 않다 — 묻지 않는다. `tools/`·`.claude/`·문서를 고치지 않는다. Workflow 결과 파일을 열어 해석하지 않고 숫자를 고치지 않는다.
커밋·push는 `live_tick.sh`가 한다 (main에 바로). 시각은 KST로 쓴다.

0. **최신 main:** `git checkout main && git fetch origin main && git merge origin/main` (같은 세션이 다시 깨어나므로 앞 실행 뒤의 커밋을 받는다). 이 절을 다시 읽는다.

1. **판정:** `bash tools/solo_raid/live_tick.sh plan` → JSON 한 줄 (`action`·`T`·`start`·`end_w`·`after`·`trigger`·`reason`).
   - `idle` → 6으로 (보통 할 일 없음. `after`가 있으면 예약 작업만 손본다).
   - `stop` → `update_trigger(enabled=false)` 뒤 7로 (「멈춤: {reason}」).
   - `run`(예측 칸) · `final`(종료 후 수집) → 2로.
2. **받기:** `bash tools/solo_raid/live_tick.sh collect`를 **Bash `run_in_background`(timeout 7200000)** 로 띄우고 완료 알림을 기다린다 (대기 루프를 짜지 않는다).
   칸 경계 전이면 스스로 기다린다. 실패하면 같은 인자로 한 번 더 돈다.
   - 종료 0 → 출력 끝 줄 JSON(`WORK/workflow.json`과 같음)으로 3. `needed`가 false면 4·5를 건너뛰고 5의 `finish`로.
   - 종료 4 (403·429) → `bash tools/solo_raid/live_tick.sh fail collect "403·429"` → `update_trigger(enabled=false)` → 7 (「멈춤: 403·429 — 이 시즌 받기를 멈췄다」).
     다시 켜는 것은 사용자가 정한다.
   - 그 밖 → `bash tools/solo_raid/live_tick.sh fail collect` → 7 (다음 칸이 이어 받는다).
3. **판독:** Workflow를 **4개 한 번에** 띄운다 — `Workflow(scriptPath=".claude/workflows/raid-window.js", args={workflow.json의 args, part: 0})` … `part: 3`.
   (`args`에 `parts: 4`가 들어 있다.)
   **Workflow 도구가 없으면** (`ToolSearch`로도 안 나옴 — 2026-11-14 S43에서 확인. 계정·플랜·네트워크·레포 설정 탓이 아니다: 같은 컨테이너에서 새로 띄운 `claude -p`에는 Workflow가 있고 클라우드 세션 자체에만 없다 — 세션을 띄우는 쪽의 도구 구성, 레포에서 못 고침) 대신 세션이 직접 띄운다:
   `bash tools/solo_raid/live_tick.sh jobs` → 표준 출력 한 줄이 일감 하나(JSON `label`·`out`·`prompt`).
   줄마다 `Agent(subagent_type="raid-vision", model="haiku", description=label, prompt=그 prompt 그대로, run_in_background=true)`를
   **한 응답에서 모두** 띄우고 완료 알림을 다 기다린다 (대기 루프를 짜지 않는다). Haiku라 상시 허락이다 (AGENTS.md).
   에이전트의 한 줄 답과 결과 파일은 열어 해석하지 않는다 — 4로 간다. 일감이 0개면 4로.
4. **합치기:** `bash tools/solo_raid/live_tick.sh merge`.
   - 종료 0 → 5.
   - 종료 3 (빠진 배치) → 출력 끝 줄 JSON 목록을 `args.skip`으로 더해 3을 **한 번만** 다시 → `merge` 다시. 또 3이면 그대로 5로 (빠진 칸은 merge.json에 남는다).
     Workflow 없이 했으면 `bash tools/solo_raid/live_tick.sh jobs '{끝 줄 JSON}'`로 남은 일감만 받아 같은 방법으로 다시 띄운다.
   - 종료 5 (final만, 원본 대기 사진) → `bash tools/solo_raid/live_tick.sh collect --orig`(2처럼 background) → 3 → 4 (한 번만).
   - 그 밖 → `bash tools/solo_raid/live_tick.sh fail merge` → 7.
5. **마무리:** `bash tools/solo_raid/live_tick.sh finish`를 **Bash `run_in_background`(timeout 7200000)** 로 띄우고 완료 알림을 기다린다 (M3 계산이 최대 약 80분 — 대기 루프를 짜지 않는다, 2026-11-07).
   - `run`: 내보내기·커밋(`S{n} 받기 T{T}`)·push → F 예측(`predict_run.sh`, 몇 초~1분) → M3 예측(`m3_live.py`, 몇 분~1시간, 실패·75분 넘음이면 대체(F)) →
     `predict/T{T}/`·후처리 파일·README 줄 커밋(`S{n} 예측 T{T}`, 대체면 `(대체(F))`)·push.
     출력 끝에 M3 `[요약]` 줄과 경고(`!!`), 이어서 F 요약(참고)이 나온다. 종료 1은 F·M3 둘 다 못 낸 것이다 (이미 기록·커밋됨). 예측이 커밋됐으면 `publish.yml`을 한 번 돌려 웹을 바꾼다 — push로는 돌지 않는다 (2026-11-01,
     [publish 「언제 복사하나」](publish.md#언제-복사하나)). `final`이 끝난 뒤에도 한 번.
   - `final`: 내보내기·커밋·push → `post_all.sh` → `live/final_done.json`, `live.json`의 `season`을 비움 → 커밋(`S{n} 종료 후 수집 끝`)·push.
   - 종료 1 (예측 실패) → 이미 기록·커밋됐다. 7로.
6. **예약 작업 손보기** (1의 `after`, `update_trigger` 도구가 있을 때만):
   - `set_once {시각}` → `update_trigger(trigger_id={trigger}, run_once_at={시각})`. 반복 일정이 e_end 한 번짜리로 바뀌어 그사이 빈 깨우기가 없어진다
     (T_end 칸, 또는 종료 뒤 `idle`인데 아직 반복일 때. `get_trigger`가 되면 이미 그 시각 한 번짜리인지 먼저 본다).
   - `finish` → 한 번짜리면 실행 뒤 저절로 꺼진다. 아직 반복이면 `update_trigger(enabled=false)`.
   - 도구가 없거나 실패해도 수집은 돈다 — 반복 일정이 매일 05:01에 깨우므로 e_end 05:01에 종료 후 수집이 그대로 돌고, 그사이 깨우기는 `idle`이다.
     이때 7의 답과 알림에 「예약 작업을 못 바꿨다 — 끝나면 사람이 꺼야 함」을 적는다.
7. **마지막 답** (세션 기록에 남는다. 해석을 덧붙여 확신을 키우지 않는다).
   **알림:** 실패·멈춤, 첫 예측(T=6), 마지막 예측(T_end), M3 대체(F) 칸, 종료 후 수집 끝, 예약 작업을 못 바꿨을 때만 `PushNotification`(status proactive)으로 첫 줄과 등급·사유를 한두 줄 보낸다
   (지연 도구라 처음 쓸 때 `ToolSearch`의 `select:PushNotification`으로 불러온다).
   그 밖의 칸은 알리지 않는다 (하루 4번 알림을 피함).
   - `run`: 첫 줄 `S{n} T{T} 예측 — {칸 시각} 칸, {올린 시각} 올림` (대체면 끝에 「· 대체(F)」). 다음에 `finish` 출력의 M3 `[요약]` 줄과 `!!` 경고를 그대로 (F 요약은 한 줄로 줄여 「F 참고」), 받은 글·시트·요청 수를 한 줄로.
     맨 끝에 「검증 안 된 예측」.
   - `final`: 받은 글·관측 수 한 줄과 8에서 연 끝난 뒤 보강 세션 주소 (못 열었으면 「끝난 뒤 보강 세션을 못 열었다 — 「S{n} 끝난 뒤 보강 해」를 시켜야 함」, 알림에도).
   - `idle`: `reason` 한 줄 (예약 작업을 손봤으면 그것도).
   - 실패·멈춤: 어느 단계에서 왜(`run.log`·FAILED 끝 몇 줄 요약), 다음 칸이 이어 받는지.

8. **끝난 뒤 보강 세션 열기** (`final`이 끝까지 됐을 때만 — 2026-11-01 사용자 결정). 7의 답을 쓰기 전에 `create_session`(지연 도구면 `ToolSearch`로 불러온다)으로
   `source_url` = `https://github.com/jgaram/nikke-community`, `model` = `claude-opus-5-5`, `permission_mode` = `auto`, `title` = `S{n} 끝난 뒤 보강 (자동)`,
   `prompt` = 아래 [끝난 뒤 보강 프롬프트](#끝난-뒤-보강-프롬프트)의 `{n}`을 바꾼 것. 한 번만 연다 — `live/final_done.json`에 `postseason_session`을 적고 커밋·push한다
   (이미 있으면 다시 열지 않는다). 도구가 없거나 실패하면 열지 않고 7의 답·알림에 적는다 (사람이 「S{n} 끝난 뒤 보강 해」를 시키면 같은 일이 된다).

### 놓친 칸·겹침

- 구간은 「지난 성공 끝」(`state/runs.jsonl`)부터라 실행 하나가 실패해도 자료는 빠지지 않는다. 다음 칸이 그만큼 길게 받는다.
- 놓친 T의 예측은 나중에 메우지 않는다 (그 뒤 글이 섞인다). README 「자동 실행」 표에 실패로 남는다.
- 같은 칸을 두 번 하지 않는다: `plan`은 `predict/T{T}/`가 있으면 `idle`, `finish`는 main에 그 예측이 먼저 올라왔으면 예측을 건너뛴다.
- 리허설: `LIVE_DATA`(사본 `data/solo-raid`)·`LIVE_NOW`(가짜 지금)·`LIVE_DRY=1`(커밋·push 안 함)·`LIVE_WORK`(작업 폴더)로 레포를 건드리지 않고 돌린다.

## 3. 끝난 뒤 (e_end 이후)

1. **남은 구간·후처리:** 자동이다 (종료 후 수집 실행). `[지난 끝, e_end)`를 받고 판독·합치기, 원본 대기 실행, `post_all.sh`까지 한다.
2. 아래 3~7은 종료 후 수집 실행이 연 **끝난 뒤 보강 세션(Opus)** 이 사람 없이 한다 (2026-11-01 사용자 결정 — 전에는 사용자가 「S{n} 끝난 뒤 보강 해」라고 시킨 세션이 했다. 지금도 그렇게 시키면 같은 순서로 한다).
   사람이 보고 있지 않으니 묻지 않는다. 멈추는 곳은 [일괄 수집 「멈출 때」](solo-raid-backfill.md#멈출-때)와 같다 — 같은 단계가 두 번 실패하면 커밋·push 뒤 알리고 끝낸다.
   **순서가 중요하다 (2026-10-17):** 채점(4)은 그 시즌 정답으로 도구·설정·보정을 고치기 전에, 수집 끝 표시(5) 전에 한다.
   수집 끝 표시가 있어야 등록부·정답 표·검증이 그 시즌을 쓰므로, 표시를 먼저 하면 채점 전에 분석 도구가 그 시즌 정답을 연다 ([분석 4.5](solo-raid-analysis.md#45-고정과-미래-시험)).
3. **데이터 점검:** [일괄 수집 「7. 데이터 점검」](solo-raid-backfill.md#7-데이터-점검-s34-이하실시간)과 같다. 원본 기준 예외 처리(`discard.json`)만 한다 —
   점검에서 나온 「다음 시즌에 바꿀 것」(도구 고침)은 4의 채점 뒤에 한다 — 자동 세션은 도구를 고치지 않고 README 「다음 시즌에 바꿀 것」에 적기만 한다.
   **판단은 Opus가 원본 사진을 직접 보고 [예외 처리 규칙](solo-raid-backfill.md#예외-처리-규칙)대로 한다.** 규칙으로도 못 정하는 후보는 고치지 않고 `decision: later`(`note`에 사유)로 둔 채 다음 단계로 간다 — 관측은 그대로 남는다.
   `later` 수와 항목은 7의 끝 알림에 적어 사람이 나중에 본다.
4. **자기 예측 채점 (먼저):** `python3 -I tools/solo_raid/score_live.py S{n}` → `predict/score.json` 커밋, 표를 채팅에 옮긴다 (판 2에는 잠긴 시즌이 없어 `--final`은 쓰지 않는다).
   M3 시즌(S43부터)은 표가 [M3]·[F] 둘로 나오고 끝에 M3 score 한 줄 (연구와 같은 셈 — `m3_summary`)이 나온다. **M3 줄이 웹에 나간 예측의 미래 시험이다** (대체(F) 칸 포함, 칸 수를 적는다) —
   S43이 M3의 첫 실전 시험이다 ([method 「WP7」 4](solo-raid-method.md#wp7-운영-반영--사용자가-wp6에서-지시할-때만-2026-11-01-계획만--원칙-1)). 결과 한 줄을 method 문서 「WP7 결과」에도 적는다.
   끝나기 전에 커밋된 예측을 고치기 전에 한 번 채점한 결과라 독립 시험 기록이다 (모든 새 시즌, split 판 2 — 2026-10-17 사용자 결정).
   T마다 도구 커밋이 다를 수 있으니 `run.tool_head`별로 적는다 — `score.json`의 `runs`(T마다 도구 커밋·prior·core sha1)·`tool_heads`에 있고, 표준 출력 표에도 T마다 나온다 (2026-10-17).
   방법(고정 모델 이름 또는 「prior 하나」)이 둘 이상이면 방법별로 나눠 적는다 (`methods`, 줄의 `method`). S42는 T6~T24를 F로 다시 내서 파일로는 모두 F다 — T6~T24는 T30 뒤에 낸 재산정이라 T30~ 진행 중 예측과 나눠 적는다 (`recalc`, 2026-10-18).
   원래 S41 prior 예측도 채점하려면 위 원래 커밋의 파일로 한다.
   채점 기준은 `criteria.json` 판 1(sha1 `80c63e2f`, `score.json`의 `criteria_sha1`)이다 — S42 채점용으로 고정 (분석 4.0a).
5. **수집 끝 표시:** `$DEST/collect_done.json` (`{"done": "KST 시각", "by": "세션 id"}`) → 커밋. 이 표시가 있어야 분석 도구가 이 시즌을 쓴다.
6. **분석 갱신:** [일괄 수집 「8. 분석 갱신」](solo-raid-backfill.md#8-분석-갱신)의 3~5와 같다.
   채점(4)이 먼저다 — 채점 뒤에는 어느 시즌이든 개발에 넣는다 (split 판 2).
   (전에는 「시험 시즌은 채점·분석을 하지 않고 정답 수치를 쓰지 않는다」였다 — 공개 결정 A로 끝난 시즌 정답은 공개한다.)
6b. **다음 시즌 M3 고정 (M3 시즌만, 6 뒤 — 2026-11-07):** `python3 -I tools/solo_raid/m3_post.py all --season S{n}` (`--season`은 **끝난 시즌**). 4~7시간 걸린다 —
   `setsid nohup python3 -I tools/solo_raid/m3_post.py all --season S{n} > ${TMPDIR:-/tmp}/m3_post.log 2>&1 < /dev/null &`로 띄우고,
   Bash `run_in_background`(timeout 7200000)로 `while pgrep -f "m3_post.py all" > /dev/null; do sleep 60; done; tail -30 ${TMPDIR:-/tmp}/m3_post.log` 대기를 건다.
   2시간 한도로 대기가 끝나면 같은 대기를 다시 건다. 컨테이너가 바뀌어 프로세스가 없고 끝 줄도 없으면 같은 명령을 다시 띄운다 (이미 된 단계·칸은 건너뛴다 — 칸마다 저장, 묶음마다 커밋·push).
   하는 일: 끝난 시즌을 1단계에 더함 (`analysis/m3/stage1.json` + 고정 사본 `stage1_through_S{n}.json`, 약 6분) → 그 시즌 되돌려 보기 20칸 (고정 S{n} 모델·끝난 자료 → `analysis/m3/backtest/pred_S{n}.json`, 3~6시간 — 다음 보정 풀·웹)
   → 다음 시즌 꼴 (`analysis/m3/shape_hist.json` · `S{n+1}/shape.json`) → `m3_freeze.py --season S{n+1}` (M3·F 모델 파일) → 웹 되돌려 보기 `backtest_M3.json`. 단계마다 스스로 커밋·push한다.
   필요한 것: 채점(4)·수집 끝 표시(5)·분석 갱신(6 — 정답 표 `answer_key.json`에 그 시즌이 있어야 꼴 단계가 돈다)이 먼저, `tools/solo_raid`에 커밋 안 된 변경 없음, 그동안 다른 무거운 계산 없음.
   실패하면 멈추고 알림에 단계와 로그 끝을 적는다 (다음 시즌 켜기 전에 사람이 본다). 다음 시즌 일정이 05시 시작 120시간이 아니면 고정 단계가 멈춘다 — 그대로 알린다.
7. README 「시즌 요약」을 채우고 (일괄 수집 형식 + 「예측」 칸: 시점마다 커밋 시각과 등급 — 「자동 실행」 표에 있다 — + 4의 채점 한 줄) 사용자에게 끝을 알린다.
   마지막 push 뒤 `publish.yml`을 한 번 돌린다 ([publish 「언제 복사하나」](publish.md#언제-복사하나) — `analysis/**`·`registry.json`이 바뀌었다).
   알림은 `PushNotification`(status proactive) 한 번: `S{n} 끝난 뒤 보강 끝 — 채점 {1·3% |e| 요약}, 점검 후보 {c}·고침 {f}·later {l}, 분석 갱신 {등급}`. 실패·멈춤도 알린다.

### 끝난 뒤 보강 프롬프트

```
솔로레이드 S{n} 끝난 뒤 보강. docs/solo-raid-live.md의 「3. 끝난 뒤」 3~7을 순서대로 그대로 따른다 (종료 후 수집 실행이 이 세션을 열었다).
사람이 보고 있지 않으니 묻지 말고, 그 절이 멈추라고 하는 곳에서만 멈춘다. 채점(4)을 수집 끝 표시(5)보다 먼저 한다.
점검에서 규칙으로 못 정하는 후보는 later로 두고 넘어간다. 마지막 답과 알림은 그 절의 형식대로 한국어로 쓴다.
```

절차는 이 문서에 두므로, 절차를 바꿀 때 이 프롬프트는 고치지 않는다.
