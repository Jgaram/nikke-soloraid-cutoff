# 솔로레이드 지난 시즌 일괄 수집 (S40 → S19)

2026-10-16 KST 사용자와 정한 계획과 실행 지시문. 지난 시즌 22개(S40~S19)를 역순으로 모아 시즌마다 `data/solo-raid/S{n}/`에 커밋한다.
수집 방법·도구의 정본은 [저비용 수집 실험](../experiments/2026-10-15-solo-raid-low-cost/README.md)의 「남은 일 (두 세션 합침)」이고, 이 문서는 그것을 여러 시즌에 돌리는 순서만 정한다.

| 파일 | 내용 | 누가 고치나 |
|---|---|---|
| 이 문서 | 계획, 조율·시즌·점검·분석·시험 세션 지시문 | 사람 (시범 결과로 고칠 때) |
| `data/solo-raid/seasons.json` | 시즌마다 `season.json`에 넣을 값과 받기 구간 | 시즌 세션이 확인 결과(`check`)를 반영할 때만 |

| `data/solo-raid/S{n}/` | 상태·실행 기록·시즌 요약 `README.md`, 점검 기록(`discard.json`·`review.json`·`review_fetch.tsv`), 수집 끝 표시(`collect_done.json`) | 그 시즌 세션만 (끝난 시즌은 점검 세션도) |

## 조율 세션 지시문

시작: 새 세션에서 `docs/solo-raid-backfill.md의 조율 세션을 실행해`. 모델은 Sonnet이면 충분하다.

조율 세션은 사이트에 요청하지 않고, 시즌 데이터를 열지 않는다. 시즌 세션을 띄우고 알림을 받아 진행표를 고치는 일만 한다.

1. **준비.** `get_session`(session_id 생략)으로 자기 세션 id를 얻는다. `PROGRESS.md`를 읽어 상태를 확인한다 (이어서 하는 경우 「받는 중」·「판독 중」인 세션을 `get_session`으로 확인).
2. **시즌 세션 띄우기** (`create_session`):

   - `prompt`: `docs/solo-raid-backfill.md의 「시즌 세션 지시문」을 S{n}으로 실행해. 조율 세션 id: {자기 id}. Haiku Workflow는 AGENTS.md에 따라 상시 허락이다.`

3. **순서.**

   - `S{n} 확인 필요 …` (S19·S26의 기준 판단이 애매할 때) → 사용자에게 그대로 묻고, 답을 그 세션에 `send_message`로 전한다.
   - `분석 {ⓝ}: …` (중간 소식) → 사용자에게 한두 줄로 전한다. 시즌 세션에 알릴 도구 변경이면 받는 중인 시즌 세션에도 `send_message`로 전한다.
   - `분석 {ⓝ} 끝 …` → 진행표 머리말의 분석 줄에 적고 사용자에게 알린다. 다음 구간이 이미 모두 끝났으면 바로 띄운다. ④면 시험 세션을 띄운다.
   - `시험 끝 …` → 진행표에 적고 사용자에게 그대로 알린다.
5. **점검.** 알림이 빠질 수 있으므로 `send_later`로 약 60분마다 스스로 깨운다. 깨면 받는 중·판독 중인 세션과 돌고 있는 분석·시험 세션마다 `get_session`을 본다.
   - `status_bucket`이 `failed`이거나, 알림 없이 끝나 있으면 `list_events`(kinds `assistant`·`result`, 최근 것)로 마지막 상태를 보고 진행표를 고친다.
   - 받기 단계에서 멈춘 것이면 슬롯을 비운다. 되살리려면 같은 세션에 `send_message`로 「이어서 해」를 보낸다 (컨테이너가 새로 떠도 `state_sync import`로 잇는다).
6. **끝.** 모든 줄이 「완료」 또는 「멈춤」이고 분석 ④와 시험 세션이 끝나면 사용자에게 한 번에 보고하고, 남은 `send_later`를 지운다.

진행표를 고칠 때는 `git fetch origin main && git merge origin/main` 뒤 커밋하고 `git push origin HEAD:main`. 시즌 세션은 이 파일을 고치지 않으므로 충돌하지 않는다.

## 시즌 세션 지시문

시작 문구는 조율 세션이 넣는다. 읽을 것은 이 절, `data/solo-raid/seasons.json`의 자기 시즌, 저비용 실험 README의 「남은 일 (두 세션 합침)」과 「기간 한 번 돌리기」뿐이다
(S34 이하는 아래 「예외 처리 규칙」도). 실험 기록을 처음부터 읽지 않는다.

변수 (예: S39):

```bash
N=39
REPO=$(git rev-parse --show-toplevel)
L=$REPO/experiments/2026-10-15-solo-raid-low-cost      # 도구는 $L/tools, 명령은 $L에서 돌린다
STATE=<세션 임시 폴더>/S$N                              # 레포 밖. 사진·OCR venv가 여기 생긴다
DEST=$REPO/data/solo-raid/S$N
export DCNET_UA="nikke-community-research/0.1 (+https://github.com/jgaram/nikke-community)" COLLECT_WORKERS=4 DCNET_GAP=0.5
```

### 1. 준비

- 세션 시작 훅이 「push 안 된 커밋 N개」라고 하는데 `git merge origin/main`이 `refusing to merge unrelated histories`면, 로컬 main이 옛 이력이다 (S40 시범 2026-10-16: 49개 모두 원격에 같은 내용이 있었다).
  `git branch -m main local-main-backup && git checkout -b main origin/main`으로 옮긴다 (지우지 않는다). 그 뒤 `raid-vision` 에이전트가 세션에 나타난다.
- `$DEST/state/`가 있으면 `python3 -I tools/state_sync.py import "$DEST" "$STATE"`로 잇는다. `$DEST/README.md`의 「진행」에서 끝난 단계를 확인하고 이어서 한다.
- 처음이면 `seasons.json`의 자기 시즌 항목에서 `name`·`boss`·`start`·`end`·`c_start`·`e_start`·`e_end`를 골라 `$STATE/season.json`을 만든다 (`windows`·`check`·`note` 등은 넣지 않는다).
- `$DEST/README.md`를 만든다. 「진행」 칸에 단계별 끝난 시각을 적어 간다 (아래 「시즌 요약」 형식).

### 2. 확인 단계 (`check`가 있는 시즌만)

- **`first_day_open` (S26·S19):** 재시작 첫날부터 챌린지가 열렸는지 본다.
  1. `season.json`의 `c_start`·`e_start`를 잠시 `start`로 바꾸고, 구간 `[start, 기본 c_start)`를 아래 3·4단계처럼 한 번 돌린다 (받기 → 판독 → 합치기).
  2. 그 구간 관측(`obs.jsonl`의 그 run)에 **이번 시즌 랭킹의 % 또는 순위 화면**이 있는지 본다. 점수가 `seasons.json` `kr_cut_10`의 절반 이상인 줄이 서로 다른 글 2개 이상에 있으면 첫날 오픈으로 본다. 없으면 3일차 규칙이 맞다.
  3. 판단에 따라 `c_start`·`e_start`를 정하고 `seasons.json`의 자기 항목(`c_start`·`c_start_basis`·`check: null`)도 고친다. 3일차가 맞으면 그 구간 줄은 시즌 밖으로 다시 거른다 (`merge_obs.py`를 그 run에 다시 돌림, 요청 0).
  4. 근거가 애매하면 조율 세션에 `S{n} 확인 필요: {근거 요약}`을 보내고 답을 기다린다. 그동안 3일차 이후 구간 받기는 진행해도 된다.
- S28은 확인을 마쳤다 (아래 「S28 재개 확인」). `seasons.json` 값을 그대로 쓴다. 재개 전 화면을 재개 뒤에 올린 글은 시즌 거르기가 첨부 시각으로 가르게 두고, 따로 지우지 않는다.

### 3. 받기 단계 (사이트 요청, 동시 2개 슬롯 안)

`seasons.json`의 `windows` 구간(S31 이하는 네 구간)을 차례로 돈다. 구간마다:

1. `bash tools/run_window.sh "$STATE" '{구간 시작}' '{구간 끝}'`를 **Bash `run_in_background`(timeout 7200000)로 하나만** 띄우고 완료 알림을 기다린다. 대기 루프를 짜지 않는다.
2. `RUN/DONE`이 있으면 한 줄 요약을 `README.md`에 적는다. `RUN/FAILED`면 같은 인자로 한 번 다시 돌린다 (받은 것은 건너뛴다).
3. `python3 -I tools/state_sync.py export "$STATE" "$DEST"` → `git add data/solo-raid/S$N` → 커밋(`S{n} 받기 {구간}`) → `git fetch origin main && git merge origin/main && git push origin HEAD:main`.
4. 한 구간의 코드 단계가 100분을 넘었으면 다음 구간을 반으로 나눠 돈다.

모든 구간이 끝나면 조율 세션에 `S{n} 받기 끝: 글 {k}개, 요청 {r}번, 실패 {f}번, 403·429 {x}번`을 `send_message`로 보낸다.

### 4. 판독·합치기 단계 (요청 0)

구간 순서대로, 구간마다:

판독 Workflow는 RUN 폴더에만 쓰고 STATE를 건드리지 않으므로, 다음 구간 받기가 도는 동안 띄워도 된다. **합치기(`merge_obs.py`)는 그 구간까지 받기가 끝난 뒤 구간 순서대로** 한다 (S40 시범에서 이렇게 해 결과가 같았다).

1. `DONE`의 `run`·`sheets`·`text_batches`·`ctx_batches`로 Workflow를 **4개 한 번에** 띄운다:
   `Workflow(scriptPath=".claude/workflows/raid-window.js", args={run, sheets, text, ctx, tile_prompt: "$L/tools/tile_prompt.md", parts: 4, part: 0..3})`.
   결과 파일을 열어 보지 않는다.
2. `python3 -I tools/merge_obs.py "$STATE" "$RUN"`. `RUN/missing.txt`가 있으면 빠진 배치만 `skip`을 주어 다시 돌린다.
3. 내보내기 → 커밋(`S{n} 합치기 {구간}`) → push.

### 5. 원본 대기 실행 (슬롯 없이 허용)

`$STATE/pending_orig.txt`가 비어 있지 않으면 `e_end` 직전 1시간 구간(`'{e_end − 1시간}' '{e_end}'`)을 한 번 더 돌린다 (새 글은 거의 없고 원본만 받는다). 그다음 4단계를 한 번 더 하고 내보내기·커밋·push.

### 6. 끝

- `$DEST/README.md`의 「시즌 요약」을 채운다 → 커밋(`S{n} 완료`, 후처리 파일 포함) → push.

### 8. 분석 갱신

분석(3~5)은 개발 시즌만 한다.

1. `$DEST/collect_done.json`을 쓴다 (`{"done": "KST 시각", "by": "세션 id"}`) — **시험 시즌도 쓴다** (수집이 끝났다는 표시. 이것이 있어야 분석 도구가 이 시즌을 끝난 시즌으로 본다).
2. 시험 시즌이면 여기서 9로 간다.
3. `git fetch origin main && git merge origin/main` 뒤 `python3 -I $REPO/tools/solo_raid/analyze_all.py` (후처리 최신 확인 → 등록부 → 정답 표 → 여러 시즌 prior → 검증, 시즌 수에 따라 10~30분).
   Bash `run_in_background`로 띄우고 끝 알림을 기다린다.
   끝나지 않은 다른 시즌은 건드리지 않는다. push 때 생성 파일(`registry.json`·`analysis/*.json`, 끝난 시즌 state의 후처리 파일)이 부딪히면
   `git checkout --theirs` 그 파일들 → `analyze_all.py`를 다시 돌린다 (결정적이라 같은 입력이면 같은 결과).
4. README에 「분석 갱신」 칸: 등록부 학습 등급, 정답 표에서 이 시즌의 채점 지점 수·흔들림, 검증 요약(`xval_dev.json` summary)이 전과 어떻게 달라졌는지 2~3줄.
   기본 prior를 바꾸지 않는다 (분석 문서 3.3 — 개발 시즌 8개 이상에서 분석 세션이 판정).
5. 커밋(`S{n} 분석 갱신`) → push.

### 멈출 때

- **403·429가 한 번이라도 나오면** (`dcnet.py`가 멈춘다) 다시 돌리지 않는다. 내보내기·커밋·push 뒤 `S{n} 멈춤: 403·429 {사이트} {시각}`을 보내고 끝낸다.
  본문 사진 서버(`dcimg*`)의 403은 그 사진만 실패로 적고 넘어가며, 한 번 실행에 20번 쌓일 때만 멈춘다 (2026-10-16 사용자 결정, 아래 「바뀐 기록」).
- 같은 단계가 두 번 실패하면 내보내기·커밋·push 뒤 `S{n} 멈춤: {단계} {RUN/FAILED·run.log 끝 몇 줄 요약}`을 보내고 끝낸다.
- **`tools/`·`.claude/workflows/`를 고치지 않는다** (다른 레인과 어긋나지 않게). 고쳐야 할 것 같으면 멈추고 알린다. 예외는 S40 시범 세션이다.
  데이터 예외는 도구 대신 기록(`S{n}/discard.json`)으로 다룬다. 규칙으로 잡을 만한 것은 「다음 시즌에 바꿀 것」에 적는다.
- S35~S37 세션은 컷을 추정하거나 분석하지 않는다. S34 이하도 컷 추정은 8단계(개발 시즌의 analyze_all)로만 한다.
  기존 컷 조사(`experiments/2026-10-14-solo-raid-cutoff/`)는 `first_day_open` 판단 기준값 말고는 쓰지 않는다.

## 예외 처리 규칙

사용자 결정 (2026-10-16): 사후 데이터 예외는 스크립트로 다 다룰 수 없다. **스크립트가 후보를 고르고, 세션이 원본을 보고 판단해 기록으로 남기고,
스크립트가 그 기록을 매번 다시 적용한다.** 그래서 같은 입력이면 같은 결과가 나오고, 판단마다 근거가 남는다.

1. **찾기.** 후처리 뒤 [`review.py`](../tools/solo_raid/review.py) `STATE --write` → `S{n}/review.json`.
   후보 종류: 정답 점 플래그(단조 위반 등), 순위표 1~3위 지문의 서버 엇갈림, 서버 묶음 섞임, 「n서버」 글의 단일 라벨, 다른 시즌 점수(지난 기록 모음),
   곡면 이탈, 200 넘는 등수(`rank_over_200`, 사진마다), 정답 흔들림(개발 시즌만). 작업 중 직접 본 이상한 것도 같은 방식으로 다룬다.
2. **원본 다시 보기.** 수집 세션은 STATE의 사진을 본다. 사진이 없으면(점검 세션 등) [`refetch.py`](../tools/solo_raid/refetch.py)로 다시 받는다 —
   **시즌당 200번 안, 자기 이름 UA** (사용자 결정). 넘겨야 하면 사용자에게 묻는다. 403·429면 멈춘다.
   사진은 세션이 직접 본다. 많으면 `raid-vision`(Haiku)에 판독을 맡겨도 되지만 판단은 세션이 한다.
3. **판단 근거는 원본에서만.**
   - 쓸 수 있는 것: 사진 속 글자·숫자, 같은 사진·같은 정확 점수가 나온 다른 글, 글 제목·본문, 순위표 상위권 정확 점수(서버·시즌 지문), 게시·촬영 시각.
   - 쓰면 안 되는 것: 커뮤니티 집계 컷·예측 결과와 맞는지, 곡선에 잘 붙는지. 그걸로 고르면 정답에 맞춰 데이터를 고치는 것이 된다.
     단조 위반·곡면 이탈은 「어디를 볼지」 고르는 데만 쓴다.
   - 근거가 모자라면 고치지 않는다 (`keep` 또는 `later`, 이유를 note에). 의심만으로 버리지 않는다.
   - **판독이 맞는지만 보지 말고, 그 줄이 「이번 시즌·그 서버·그 시각」의 화면인지 먼저 본다** (2026-10-16, S33 점검을 다시 본 결과).
     곡면 이탈·단조 위반 줄은 판독이 맞는 경우가 대부분이고, 원인은 보통 지난 시즌 화면·다른 서버 화면·기록 세운 때의 %다.
     - 화면 종류와 시각: 「솔로 레이드 최종 순위입니다」(RAID RESULT) 화면이 시즌 끝 전에 올라왔으면 지난 시즌이다 (이제 post_exclude가 `final_pre_end`로 뺀다).
       같은 정확 점수가 여러 글·여러 날에 같은 %로 되풀이되면 「같은 사람 기록이라 그대로」가 아니라 지난 기록 화면을 다시 올린 것인지 본다.
     - 서버: 순위표 1~7위 이름·길드·정확 점수가 어느 서버 라벨 글들과 같은지 본다 (예: S33 MIDNIGHT·BENGDA = 글섭).
     - |z| 8 이상 곡면 이탈과 등급 A·A2 정답 점 플래그는 항목마다 원본을 본다.
     - **200 넘는 등수 (`rank_over_200`, 2026-10-16).** 게임 화면 등수는 200위까지다 (사용자 확인). 원본에서 그 숫자가 무엇인지(배지·레벨 등) 보고,
       같은 줄의 %·점수도 잘못 읽혔는지 본다. %·점수가 맞으면 `keep`(등수는 도구가 이미 비운다), 틀렸으면 줄 버림(`scope: row`, 바른 값은 `correct`에),
       게임 화면이 아니면(다른 사이트 캡처 등) 그 사유대로. 같은 사진의 여러 줄은 한 항목이다.
       S32~S41 265장은 모두 아바타 아래 계정 레벨 배지·%·점수 맞음(keep)이었다 — 같은 꼴이면 사진 몇 장만 보고 묶어 판단해도 된다 (note에 본 사진).
4. **기록.** `S{n}/discard.json` 항목 (꼴은 [`discard.py`](../tools/solo_raid/discard.py) 머리말):
   글 버림(`action: discard`) · 서버 고침(`action: server`, 판독은 맞고 서버만 틀림) · 줄 버림(`scope: row`, 판독 틀림 — 바른 값은 `correct`에 기록만).
   `reason`에 근거를 구체적으로(사진 id, 같은 점수 글 번호), `by`에 세션, `decided`에 날짜. `review.json` 항목에는 `decision`·`note`·`by`·`decided`,
   그리고 `seen`(이 항목을 판단하며 원본으로 본 사진 id 목록, 안 봤으면 빈 목록과 note에 이유). note는 항목마다 그 항목의 근거를 쓴다 —
   다른 항목의 note를 그대로 붙이지 않는다 (같은 원인으로 묶어 판단했으면 「○○와 같은 원인: {그 사진에서 본 것}」). 2026-10-16.
   글 하나에 서버가 다른 사진이 섞였으면 사진 단위 서버 고침(`scope: img, action: server`)을, 이어붙인 사진 한 줄만 다르면 줄 단위(`scope: row, action: server`)를 쓴다 (줄을 버리지 않는다).
   원자료(obs.jsonl 등)는 고치지 않는다.
5. **다시 돌리기.** `post_all.sh` → `review.py` 다시. 고친 후보가 사라졌는지, 새 엇갈림이 생기지 않았는지 본다.
6. **도구 코드는 고치지 않는다** (병렬 세션끼리 도구가 어긋나지 않게, 사용자 결정). 규칙으로 잡을 만한 것은 README 「다음 시즌에 바꿀 것」에 적고, 분석 세션이 모아 고친다.
7. **시험 시즌.** 같은 규칙으로 점검·예외 처리를 하되 집계표(seasons.json 컷·server_cutoffs.csv)·예측과 견주지 않고,
   README·보고·review note에 정답 점·컷 수치를 쓰지 않는다 (`review.py`는 시험 시즌이면 값 칸을 비우고 정답 흔들림을 고르지 않는다). 정답 표·검증·채점은 3.7에서 한 번.

시즌 세션 지시문의 1·2·8단계는 하지 않는다. 다른 점만 적는다.

1. **준비.** 변수는 시즌 세션 지시문과 같다. `python3 -I tools/state_sync.py import "$DEST" "$STATE"`로 잇는다.
   `$STATE/season.json`의 `e_end`만 `seasons.json`의 새 `e_end`로 바꾼다 (후보 규칙 E의 기간이 여기서 나온다). 다른 값은 그대로.
   `$DEST/review.json`의 항목 id 목록을 세션 임시 폴더에 적어 둔다 (7에서 새 항목만 고르려고).
2. **받기.** `windows`의 **넷째 구간 하나만** 시즌 세션 지시문 3단계대로 돈다. `run_window.sh`는 반드시 Bash `run_in_background`(timeout 7200000)로 띄운다 — `nohup … &`로 띄우면 끝 알림이 오지 않아 세션이 쉰 채 멈춘다 (S40 소급, 2026-10-16). 커밋 이름 `S{n} 받기 +2~+4일`. 끝나면 조율 세션에 `S{n} 소급 받기 끝: 글 {k}개, 요청 {r}번, 실패 {f}번, 403·429 {x}번`.
3. **판독·합치기·원본 대기.** 시즌 세션 지시문 4·5단계대로 (원본 대기 구간은 새 `e_end` 직전 1시간). 커밋 이름 `S{n} 합치기 +2~+4일`.
4. **후처리.** `git fetch origin main && git merge origin/main` 뒤 `bash $REPO/tools/solo_raid/post_all.sh "$DEST/state"`.
   다른 세션(등수 점검 등)이 같은 시즌의 `review.json`·`discard.json`·`README.md`나 후처리 파일을 고쳤을 수 있다. 부딪히면 그쪽(`--theirs`)을 받고 후처리를 다시 돌린다.
5. **점검.** `review.py "$DEST/state" --write` 뒤, 1에서 적어 둔 목록에 **없던 항목만** 예외 처리 규칙대로 판단한다. 이미 있던 항목은 판단이 비어 있어도 건드리지 않는다 (등수 점검 세션 몫).
   고친 것이 있으면 후처리 → `review.py`를 다시. 시험 시즌(S34·S37)은 수치를 쓰지 않는다.
6. **README.** 「기간」 줄의 받기 끝을 새 `e_end`로 고치고 「(+2~+4일 소급 2026-10-16)」을 붙인다. 「진행」 표에 구간 4·원본 대기 줄을 더하고, 「결과」의 수치를 새 값으로 고친 뒤 끝에 `+4일 소급으로 늘어난 것: 관측 in +{}, use +{}, 글 주장 +{}`을 적는다.
   「데이터 점검」에 `+4일 소급 점검: 새 후보 {}개 — 판단별 수, 고친 것`. 커밋(`S{n} 소급 +4일 완료`) → push.
7. **분석은 돌리지 않는다** (`analyze_all.py` 안 돌림). `collect_done.json`은 그대로 둔다. 분석 세션이 후처리 도장으로 바뀐 시즌을 찾아 다시 돈다.
8. **보고.** 조율 세션에 `S{n} 소급 끝: 구간 4 글 {k}개·요청 {r}번(403·429 {x}), 관측 in {전}→{후}, use {전}→{후}, 새 점검 후보 {c}개·고침 {f}개`를 보내고 끝낸다.
   멈출 때는 시즌 세션 지시문 「멈출 때」대로 하되 알림 머리를 `S{n} 소급 멈춤:`으로 쓴다.
