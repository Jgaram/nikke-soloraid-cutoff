# 공개 레포와 웹 (nikke-soloraid-cutoff)

2026-10-16 사용자 결정. 솔로레이드 **코드와 파이프라인**을 공개 레포로 나누고, 커트라인을 **웹**으로 보여 준다.
이 레포(nikke-community)는 비공개로 남아 정본이 되고, 수집한 자료도 여기에만 둔다.

## 정한 것

- **공개 범위는 솔로레이드 파이프라인만이다.** 문서 `docs/solo-raid-*.md`(새로 만든 것도 자동)·`community-access.md`와 이 문서를 공개한다.
  코드는 `tools/solo_raid/`·`tools/publish/`, 수집 단계 `experiments/2026-10-15-solo-raid-low-cost/`의 `tools/`·`README.md`다.
  그 밖에 `.claude`의 raid-vision 에이전트·워크플로, 설정 `split.json`·`criteria.json`을 공개한다.
  목록은 `build_public.py`의 `ALLOW`가 정본이다 (허용 목록 방식 — 새 파일을 공개하려면 여기에 더한다).
- **웹에는 숫자와 개수만 싣는다.** 원글 링크·글 번호·사진·닉네임은 넣지 않는다 (사용자 결정).
  근거는 컷 예측이면 「커뮤니티 데이터 N개」(그 서버 예측에 쓴 사람 수), 지난 시즌 컷이면 출처 종류 「집계표」·「관측 곡선」으로만 쓴다 (2026-10-16 사용자 결정 — 서버를 합친 시즌 전체 관측 건수는 컷의 근거가 아니라서 뺐다).
- **끝난 시즌 기록은 시험 시즌까지 빠짐없이 공개한다 (2026-10-17 사용자 결정 「A」, 3.7 시험이 끝난 뒤).**
  - 지난 시험 시즌 S19·S24·S29·S30·S34·S37은 3.7에서 이미 정답을 봤으니 잠가 둘 까닭이 없다. 개발 시즌과 같은 형식으로 싣는다.
  - 앞으로 모든 새 시즌도 끝나면 바로 공개한다. 새 시즌의 시험은 **시즌이 끝나기 전에 커밋된 예측**(`S{n}/predict/`)만 끝난 뒤 한 번 채점하는 방식으로 한다
    (split 판 2 — 2026-10-17 사용자 결정 「모든 새 시즌 통일」로 판 1의 시험 몫 S44·S46·S48 … 규칙은 접었다, [분석 4.0](solo-raid-analysis.md#40-먼저-정할-운영-규칙-분석-전에)).
    끝난 뒤 바꾼 도구로 그 시즌을 다시 돌린 결과는 시험이 아니라 개발이다. 정답을 웹에 낸다고 시험이 깨지는 것이 아니라, 정답을 보고 방법을 고치면 깨진다.
  - 이로써 「공개 웹을 분석 세션이 읽어도 블라인드가 깨지지 않게」 잠그던 장치는 끝난 시즌에는 쓰지 않는다. 진행 중인 시즌은 원래 정답이 없다.
  - **코드 반영 (2026-10-17, 분석 4.0 세션).** `site.py`는 지난 시즌 컷을 `split.load_seasons(final=True)`·`load_server_cutoffs(final=True)`로 몫과 상관없이 읽고,
    `score.json`도 있으면 싣는다. 「잠김」 표시(`locked`)·「실제 컷 비교는 최종 검증 뒤」 문구·범례를 지웠고, 분석 페이지와 `viz.py`의 「시험 시즌(잠근 시즌)은 열지 않았습니다」를
    「끝난 시즌 모두 — 개발 검증, 독립 검증은 새 시즌의 미리 커밋된 예측 채점」으로 바꿨다. 공개 README도 같게.
    `conv()`(계산기 곡선)는 viz의 정답 표 시즌을 쓰므로 split 판 2 뒤로 지난 시험 6시즌도 들어간다 (따로 정할 것 없음).
    로컬 분석 도구의 `install_guard`는 그대로 둔다 (판 2에는 막는 시즌이 없다).
- **갱신은 Actions 자동 복사다.** 이 레포 `main`에 관련 경로(워크플로의 `paths`)가 push되면, `publish.yml`이 공개 레포 `main`과 `gh-pages`를 통째로 다시 만든다.
  공개 레포에 직접 커밋한 것은 다음 복사 때 사라진다.
  - 워크플로는 웹에 들어가는 자료(`analysis/`·`registry.json`·`seasons.json`·`split.json`·`S*/predict/`·`S*/state/season.json`)와 공개 코드·문서가 바뀔 때만 돈다.
    수집 중 `state/`·`runs/` 커밋에는 돌지 않는다 (2026-10-16 — 그날 `data/solo-raid` 커밋 137개 중 웹 자료를 바꾼 것은 11개였다).
  - 웹의 기준 시각은 **웹 내용이 바뀐 때**다. `site.py`가 넣는 자료와 페이지 틀로 지문(`data.json`의 `content`)을 만들고,
    지금 공개된 `data.json`과 지문이 같으면 그 기준 시각을 그대로 쓴다 (`build_public.py`가 `--prev`로 넘김). 그래서 내용이 그대로면 `gh-pages`에 커밋이 생기지 않는다.
    바뀌었으면 그 커밋(HEAD) 시각이다. 예전에는 `data/solo-raid` 아무 커밋 시각이라, 잠긴 시즌 README 커밋에도 시각이 움직였다.
  - 예측 파일·`season.json` 하나가 깨져도 그 파일만 빼고 Actions에 노란 경고를 남긴다. 지난 시즌 컷과 공개 레포 코드는 계속 갱신된다.

## 내보내기 전에 손보는 것과 검사 (`build_public.py`)

- 공개하지 않는 파일(AGENTS.md, 실험 기록, `data/` 등)로 가는 마크다운 링크는 링크를 풀고 글자만 남긴다.
- 특정 글을 가리키는 값은 가린다: 디시 글 번호(`board/gov/{번호}`, `no={번호}`, `글 {번호}`)와 첨부 파일명의 촬영 시각(`Screenshot_YYYYMMDD_HHMMSS`).
- 다음 중 하나라도 걸리면 아무것도 쓰지 않고 멈춘다. Actions run이 빨갛게 뜬다.
  - 사진·동영상·jsonl·csv·tsv 파일
  - 1MB가 넘는 파일
  - 가린 뒤에도 남은 글 번호와 디시 이미지 주소
  - 웹 파일 안의 커뮤니티 글 주소
- 원문, 사진, OCR 결과(`ocr.jsonl` 등 — 랭킹 화면의 닉네임이 들어 있음)는 허용 목록에 없으므로 나가지 않는다.

손으로 확인: `python3 -I tools/publish/build_public.py --out {임시}/pub --site {임시}/site`

## 웹 화면 (2026-10-16 사용자 결정)

첫 화면(`index.html`, `site_template.html`)은 탭 셋이다. 서버(한섭·일섭·글섭)를 바꾸면 모두 바뀐다 (방법 탭에서는 서버 막대를 숨긴다).

- **「이번 시즌」** — 아래 1(최종 컷 예측)과 2(계산기 카드: 최종 점수 ↔ 최종 %, 지금 % ↔ 최종 %).
- **「지난 시즌」** (주소 `#past`) — 아래 3(지난 시즌 커트라인), 4(실제로 낸 예측), 5(되돌려 보기), 6(시즌별 침수 비교).
- **「방법」** (주소 `#method`) — 아래 7. 다른 두 탭의 긴 설명을 모두 여기로 옮겼다.
- **설명은 방법 탭에, 데이터 탭에는 꼬리표만 (2026-10-18 사용자 결정 — 「웹사이트에서 최대한 잔설명을 빼고, 로직과 워크플로 설명하는 탭을 따로」).**
  「이번 시즌」·「지난 시즌」에는 제목·범례·단위·축과 짧은 경고 한 줄(신뢰도·관측 없음·빌린 배율 등)만 둔다. 카드 소개 문단, 그래프 아래 설명, 「선을 그리는 기준」,
  예측 방법 이름, 참고값 설명은 방법 탭으로 갔다. 카드 머리 오른쪽의 「설명」 링크가 방법 탭의 해당 절(`#method-pred`·`#method-calc`·`#method-cut`·`#method-rec`·`#method-back`·`#method-sink`)로 간다.
  「실제로 낸 예측」·「되돌려 보기」 제목에는 「독립 검증」·「개발 검증」 꼬리표를 붙인다. 새 설명을 더할 때도 데이터 탭에는 꼬리표만, 문장은 방법 탭에 쓴다.
- **재배치 (2026-10-18 사용자 결정):** 처음에는 「컷 예측」(컷 예측 · 지금 몇 %면 최종 몇 % · 지난 시즌 컷)과 「지난 시즌 살펴보기」(되돌려 보기 · 침수 비교)였다.
  계산기 곡선이 컷 예측과 같은 고정 모델이 되면서(같은 날) 「지금 몇 %면 최종 몇 %」 카드에 이번 시즌 곡선과 지난 시즌 겹쳐 보기(23시즌 곡선 × 시즌 세기, 22시즌 관측 점)가
  바탕이 다른 채로 한 그래프에 섞였고, 겹쳐 보기는 침수 비교와 내용이 겹쳤다. 그래서 이번 시즌 것(컷 예측, 두 계산기)과 지난 시즌 것(커트라인, 끝난 시즌 예측 기록, 겹쳐 보기)을 탭으로 나눴다.
  사용자가 고른 것: 겹쳐 보기만 지난 탭(침수 비교에 합침) · 두 계산기는 한 카드 · 끝난 시즌 예측은 이벤트 종료(e_end)까지 이번 탭 · 탭 이름 「이번 시즌 / 지난 시즌」.
  본문의 `#past`·`#method`·`#method-{절}` 링크를 누르면 탭이 바뀐다 (`#method-{절}`은 방법 탭의 `m-{절}` 요소로 스크롤).

1. **최종 컷 예측** (「이번 시즌」) — 진행 중 시즌의 최종 1·3·10% 컷 점수(`S{n}/predict/`). 최근 시점의 칸·시점별 그래프·표, 신뢰도와 「커뮤니티 데이터 N개」. 예측 방법 이름은 방법 탭 「컷 예측」 머리에 있다 (2026-10-18부터).
   - 등급 C·D는 가운데 숫자를 흐리게 하고 80% 구간을 앞에 둔다. 등급 사유 원문은 내부 용어라 싣지 않고 등급별 한 줄만 쓴다.
   - **화면에서는 「등급」 대신 「신뢰도」라고 쓰고 A~D 글자를 뺀다** (2026-10-17 사용자 결정 — 처음 보는 사람에게 설명이 필요했다).
     A 보통 · B 낮음 · C 매우 낮음 · D 참고용. 검증 전이라 맨 위도 「높음」이 아니라 「보통」이다. 이유 한 줄은 붙이지 않는다 (사용자 결정).
     분석 페이지(`viz_template.html`)도 같은 말을 쓴다. 예측 도구와 내부 문서는 그대로 등급 A~D다.
   - **관측이 1개 이상일 때만 숫자를 싣는다** (2026-10-17 사용자 결정). 어느 서버에도 관측이 없어 prior 곡선을 그대로 쓴 시점(예측 JSON `donor`가 `S41` — 고정 모델에서도 이 이름 그대로)은
     `site.py`가 숫자를 `data.json`에 넣지 않고, 화면은 「아직 관측 없음 · 관측 대기」 안내와 표의 「–」만 보인다. 그런 시점만 있으면 그래프도 그리지 않는다.
     다른 서버 관측을 빌려 채운 서버(`donor`가 서버 이름, 등급 D)는 그대로 싣는다 — 세 서버 중 한 곳에라도 관측이 있으면 표시.
     예측 파일 자체는 그대로 쌓는다 (끝난 뒤 채점용). S42 첫 예측(T6, 관측 0)에서 「커뮤니티 데이터 0개」인데 S41 컷이 그대로 보이던 것을 고쳤다.
   - **최종 % ↔ 점수 계산기** (2026-10-17 사용자 요청): 진행 중 시즌이고 최근 예측에 숫자가 있을 때만 계산한다 (없으면 안내 한 줄).
     처음에는 컷 칸 바로 아래였고, 2026-10-18부터 아래 2 「계산기」 카드의 첫 묶음 「최종 점수 ↔ 최종 %」다.
     「최종 X% 안에 들려면 최종 점수」와 「최종 점수가 Y억이면 최종 몇 %」 두 칸이다. `site.py`가 예측 JSON의 모든 지점(0.5~30%)을
     `curve`([%, 가운데, 80% 아래, 80% 위, 근처 관측 수])로 넘기고, 화면은 지점 사이를 log-log 직선으로 잇는다. 점수 → %의 80% 구간은
     80% 아래·위 곡선을 각각 거꾸로 읽은 것이다(지점별 구간을 이은 근사). 범위 밖은 「0.5% 안」·「30% 밖」으로 쓴다.
   - **「참고값」은 % 고정 기준이 아니라 자료 양으로 정한다** (2026-10-17 사용자 결정): 그 % 근처(×½~×2)에 옮긴 관측(예측 JSON `near_obs`)이
     5개 미만이면 컷 칸 이름과 계산기에 「참고값」을 붙인다. 예측 방법은 모든 %에 같고(관측을 prior 곡선 모양으로 옮겨 가까운 관측에 무게 — 고정 모델은 0.5~3%와 5~30%를 따로 실행),
     차이는 근처 자료 양뿐이라서다. 예전의 「10% 컷은 참고값」 고정 문장을 대신한다. S41에서 쓴 관측은 75%가 3% 안이었다.
   - **예측 방법 이름** (2026-10-18): 최근 예측의 방법을 쓴다 — 고정 모델이면 「최근 5시즌(S37~S41) 곡선 · 1·3%는 이번 시즌 침수 세기 갱신·구간 넓히기 더함」(`site.model_label`).
     **「모델 F」 같은 분석 안 이름은 웹에 싣지 않는다** (2026-10-18 사용자 결정 — 우리가 붙인 이름이라 보는 사람에게 뜻이 없음. 방법 탭 「지금 쓰는 설정」·되돌려 보기 설명에서도 뺐다. `data.json`의 `back.model`·`conv.base.name` 값은 그대로).
     10%(와 5·15·30%)는 ref 실행이라 세기 갱신·구간 넓히기가 없다 — 처음 이름(「prior + 수준 갱신·구간 넓히기」)은 모든 칸에 붙는 것처럼 읽혀 같은 날 고쳤다.
     가장 최근 예측 시즌의 앞 시점 방법이 다르면 「(S42: 24시간 예측까지 S41 한 시즌 곡선)」처럼 덧붙인다 (S42는 T30부터 바뀜 — 사용자 결정. 같은 날 T6~T24도 F로 다시 내서 지금은 붙지 않는다). 분석 페이지 머리 문장도 최근 방법을 쓴다.
     2026-10-18부터 방법 탭에 싣고, 옛 방식 이름의 「prior」는 웹에서 「곡선」으로 쓴다 (`site.method_label` — 「S41 한 시즌 곡선」·「여러 시즌 곡선」).
   - 끝났는지는 **브라우저가 종료 시각으로** 정한다 (만들 때 정하면 새 커밋이 없을 때 「진행 중」으로 남는다). 끝나면 제목이 「지난 예측」(맨 위 칸은 「마지막 예측」)으로 바뀌고,
     `score.json`(끝난 뒤 자기 예측 채점)이 있으면 실제 컷과 견주고, 없으면 「실제 컷과의 비교는 시즌 자료를 채점한 뒤 나옵니다」라고 쓴다 (2026-10-17 — 전에는 시험 시즌이면 「최종 검증 뒤」).
   - **끝난 시즌 예측은 이벤트 종료(`season.json`의 `e_end`, 챌린지 끝 +4일 — 없으면 끝 +4일로 셈)까지 「이번 시즌」 탭에 둔다** (2026-10-18 사용자 결정).
     그 동안 「이 시즌 예측은 이벤트가 끝나는 {e_end}까지 여기에 두고, 그 뒤로는 「지난 시즌」 탭의 「실제로 낸 예측」에서」라고 쓴다. 그 뒤 「이번 시즌」 탭에는
     「지금 예측을 내고 있는 시즌이 없습니다」만 남는다. 진행 중 시즌이 있으면 그것이 먼저다. 예전의 시즌 드롭다운(진행 중·끝남)은 없앴다 — 끝난 시즌 고르기는 아래 4에서 한다.
   - 새 시즌 `state/season.json`이 올라와 챌린지가 시작됐는데 예측이 아직 없으면 「첫 예측은 시작 6시간 뒤, 그 뒤 6시간마다 갱신」을 띄운다 (2026-10-16, 6시간 자동 수집 → docs/solo-raid-live.md).
     갱신 일정(6시간마다, 한국 시간 05·11·17·23시까지 올라온 자료)은 방법 탭 「작업 흐름」·「컷 예측 7. 갱신」에 쓴다 (2026-10-18 — 전에는 예측 방법 줄에 붙였다).
     진행 중 시즌은 분석 등록부(`registry.json`)에 아직 없으므로, `site.py`의 「최근 시즌」은 등록부와 함께 `S*/state/season.json` 폴더도 본다 (2026-10-16, S42에서 빠지던 것을 고침).
2. **계산기** (「이번 시즌」, 2026-10-18 — 첫 묶음 「최종 점수 ↔ 최종 %」는 위 1의 계산기를 옮긴 것). 둘째 묶음 **「지금 % ↔ 최종 %」**(처음 이름 「지금 몇 %면 최종 몇 %?」) — **컷 예측과 같은 곡선** (2026-10-18 사용자 결정, `site.curve_source`·`conv`). 0.5시간 간격. 진행 중 시즌이 있으면 그 시즌 날짜와 지금 시각으로 보인다.
   - 곡선 = 가장 최근 시즌의 마지막 예측이 쓴 고정 모델의 main prior(지금 S37~S41) × 그 예측이 이번 시즌 관측으로 고친 침수 세기(`level_update.result` — predict가 세 서버에 같은 배수로 곱함).
     세기를 아직 못 고쳤으면(한섭 라벨 사람 < 3, 옛 방식 예측) 배수 1, 폭은 prior의 τ_P. 마지막 예측이 고정 모델이 아니면 그 시즌 모델 파일(없으면 가장 최근 것)의 main prior만.
     그래서 6시간 예측마다 계산기도 같이 움직인다. 폭은 viz와 같은 셈(σ(P)·꼴 외삽·세기 폭).
   - **컷 예측처럼 두 곡선으로 나눈다** (2026-10-18 사용자 요청 — 10·30% 선이 1·3%용 곡선이라 컷 예측과 어긋났고, 띠에 M1 넓히기가 없었다).
     최종 `SPLIT`(4%) 이하 = 위 main 곡선(`conv.srv`), 80% 띠의 sd에 M1 배율 `predict.m1_factor(모델, h)`를 곱한다 (컷 예측 `widen`의 로그 반폭 ×c와 같은 꼴, 시점 h마다 — T30 ×1.36).
     그 위 = 모델의 ref prior 곡선(`conv.srv_ref`, 같은 5시즌 5~30%용) 그대로 — 컷 예측의 ref 실행처럼 세기 갱신·넓히기 없음.
     화면: 1·3% 선은 main, 10·30% 선은 ref. 「지금 % → 최종 %」는 main으로 낸 최종이 4% 위면 ref로 다시, 「최종 % → 지금 %」는 목표 %로 고른다.
     실선·점선 점검도 지점마다 그 곡선(1·3%는 넓힌 띠)으로 잰다. 바꾼 뒤 일섭 6시간 3% → 최종 79.1% (컷 예측 ref 곡선과 같음, 전 75.1%).
   - 전에는 분석 페이지 ①과 같은 23시즌 평균(`prior_dev`)이라 컷 예측과 어긋났다 (S42 T24 확인: 24시간 3% → 최종 15.8% vs 컷 예측 곡선 14.3%, 12시간 1% → 9.5% vs 8.4%). 분석 페이지 ①은 23시즌 그대로다.
   - 이번 시즌 곡선만 그린다. 지난 시즌 겹쳐 보기(시즌 버튼·관측 점·「그 시즌처럼 밀렸을 때」 점선)는 2026-10-18 아래 6 침수 비교로 옮겼다 — 굵은 선(최근 5시즌 고정 모델)과
     점선(23시즌 곡선 × 시즌 세기)의 바탕이 달라 한 그래프에서 헷갈렸다.
   - 선 점검(`CONV_RULE`)은 곡선을 맞춘 학습 시즌(지금 S37~S41)의 관측만으로, 이번 시즌 세기 없이 견준다. 2026-10-18 결과: 한섭 1·3·10% 실선·30% 점선(관측 25), 일섭 3·10% 실선·1% 점선(3), 글섭 3·10% 점선·1% 없음 (전에는 23시즌 관측으로 한섭 30%도 실선, 글섭 1%도 점선).
   시점별 표는 접어 둔다.
   - **시점 고르기는 한 줄 타임라인이다** (2026-10-16 사용자 결정 — 날짜는 드롭다운, 시간은 가로 슬라이더라 둘 다 시간 순서라는 게 안 보였다).
     슬라이더 하나가 챌린지 전체를 30분 칸으로 덮고, 바로 아래 일차 칸(진행 중이면 날짜도)이 같은 가로축에 붙는다. 칸을 누르면 하루 안의 시각은 그대로 두고 그날로 가고,
     ◀ ▶는 30분씩 움직인다(폰에서 끌기가 거칠어서). 진행 중 시즌이면 실제 지금 시각에 빨간 「지금」 선을 긋는다. 분석 페이지 ①도 같은 모양이다(시즌 시작일을 넣으면 날짜가 붙음).
   - (옛) 지난 시즌 실제 자료 겹쳐 보기 (2026-10-16 사용자 요청 ~ 2026-10-18): 그래프 위 버튼 「끄기 · 전체 · 시즌」으로 관측 점과 「그 시즌처럼 밀렸을 때」 점선을 올렸다.
     점은 최종이 1·3·10%의 ÷1.3~×1.3인 칸을 배율 그대로 「최종이 딱 t%였다면 그때 %」에 찍었다 (평균선 대비 흩어짐 한섭 627개 ×1.24 → ×1.17, 일섭 113개 ×1.27 → ×1.23 — 7개 시즌 기준).
     2026-10-18부터 아래 6 침수 비교의 관측 점이 이 일을 한다.
   - **선을 그리는 기준** (2026-10-16 사용자 결정, `site.py`의 `CONV_RULE`): 1·3·10·30% 지점마다 최종이 그 %의 ÷1.3~×1.3으로 끝난 관측 칸을
     같은 시각 곡선과 견준다. 관측 30개·시즌 4개 이상, 치우침(log 차 중앙값) ÷1.1~×1.1, 80% 구간 포함률 0.65~0.95이면 실선,
     관측은 있는데 못 미치면 흐린 점선과 「근거 부족」, 관측 0이면 그리지 않는다. 곡선을 맞춘 그 자료로 대 보는 표본 안 점검이다.
     점검 값은 `data.json`의 `conv.check`에 있다. 화면은 범례의 「(근거 부족)」뿐이고, 기준 문장과 세 서버 지점별 관측 수·시즌·치우침·덮은 몫·실선/점선 표는
     방법 탭 「계산기 · 실선과 점선」에 있다 (2026-10-18 — 처음에는 그래프 아래 한 줄 + 접은 「선을 그리는 기준」).
     2026-10-16 결과: 한섭 1·3·10·30% 실선(1%는 ×0.93·포함 0.73으로 겨우 넘음), 일섭 3·10% 실선·1% 점선(관측 11), 글섭 1·3·10% 점선(관측 2·7·4).
3. **지난 시즌 커트라인** (「지난 시즌」 첫 카드 — 2026-10-18까지는 「컷 예측」 탭 맨 아래) — 값마다 출처(집계표 / `*` 관측 곡선). 서버마다 자료가 있는 첫 시즌부터 보이고, 자료가 있는 시즌이 둘 미만이면 그래프 없이 표만. 아직 안 끝난 시즌은 숨긴다.
   - **지점은 서버를 정해 두지 않고 기준으로 고른다** (2026-10-16 사용자 결정, `site.py`의 `CAND`·`PAST_MIN`·`past_pcts`): 1·3·10·30% 중
     값이 있는(잠기지 않은) 시즌이 **2개 이상**인 지점만 열·선을 넣는다. 그런 지점이 없으면 값이 있는 지점을 표로만 보인다.
     값은 분석 시즌이면 정답 표, 그 밖 개발 시즌이면 seasons.json 한섭 3·10%와 `server_cutoffs.csv`(서버 셋).
     2026-10-16 결과 (GLOBAL→GL 수정 뒤): 한섭 1·3·10·30%, 일섭 3·10·30%, 글섭 3·10%(8개 시즌)·30%(S36·S38). 30%가 들면 「시즌마다 크게 오르내려 참고값」 문장을 붙인다.
   - 고친 문제 (2026-10-16): 정답 표(`truth_grade.py`)가 CSV의 `GLOBAL`을 `GL`로 바꾸지 않아 분석 시즌의 글섭 집계표 값이 빠져 있었다 (글섭은 S41 `truth_table.json`만).
     이제 `split.load_server_cutoffs()`가 바꿔 주고, 정답 표와 분석을 다시 돌려 글섭 집계표 14개가 들어왔다 (2026-10-16 GLOBAL→GL 수정 뒤 다시 돌림).

4. **실제로 낸 예측** (「지난 시즌」, 2026-10-18 사용자 결정) — 끝난 시즌(종료 시각이 지난 것) 가운데 `S{n}/predict/`가 있는 시즌의 실제 예측과 채점.
   위 1과 같은 그림(마지막 예측 칸 · 시점별 그래프 · 표, `score.json`이 있으면 실제 컷)이고, 시즌이 둘 이상이면 드롭다운으로 고른다. 끝난 시즌이 없으면 카드를 숨긴다 (S42가 끝나면 처음 보인다).
   끝난 때부터 바로 보인다 — 이벤트 종료(e_end)까지는 「이번 시즌」 탭에도 같이 있다. 시즌이 끝나기 전에 커밋된 예측만 채점하므로 **독립 검증**이라고 화면에 쓴다 (아래 5는 개발 검증).

「지난 시즌」 탭의 5·6은 2026-10-18 사용자 요청이다 — 「S35를 S34 이하 자료만으로 예측했다면 시간에 따라 어떻게 변하나」, 「시즌마다 침수가 어떻게 다른가」. 처음 탭 이름은 「지난 시즌 살펴보기」였다.

5. **지난 시즌 되돌려 보기:** 끝난 시즌(S21~S41)마다 지금 운영 방법 F로, 맞힐 시즌보다 앞 5시즌 prior와 T까지 게시된 글만 남긴 사본(tr)으로 6시간마다(T6~T120, 종료 뒤 T는 뺌) 낸 1·3·10% 예측.
     시즌·지점을 고르면 시점별 가운데 값·80% 구간·실제 컷·허용 오차 띠(1·3% ±2%, 10% ±3%)와 시점별 표, 아래에 「시즌별 오차 한눈에」(12·24·48·72·96시간 오차, 허용 오차 밖은 주황 굵게, 줄을 누르면 위 그래프가 그 시즌으로, 맨 아래 허용 오차 안·80% 구간 안 시즌 수).
     자료는 `analysis/backtest_F.json` — 만드는 도구 `tools/solo_raid/backtest_web.py` (xval 결과 둘을 운영과 같은 셈으로 합침: 1·3%는 main 실행 + 앞 시즌만으로 정한 M1, 10%는 ref 실행).
     F 자체를 이 시즌들 정답을 보며 골랐으므로 **개발 검증**이라고 화면에 쓴다. 다시 만드는 때와 명령은 [분석 4.5](solo-raid-analysis.md#45-고정과-미래-시험).
6. **시즌별 침수 비교:** 「침수」 = 시간이 지나며 내 %가 밀려 내려가는 것. 세기 = `prior_dev`(끝난 시즌 모두) % 변환의 시즌 수준 배수(1 = 평균, 모든 시즌이 같은 모양이고 log 배율만 다르다고 본 값).
     위는 시즌마다 1에서 세기까지 막대사탕(눌러서 아래 그래프에 넣고 뺌, 3개까지), 아래는 「지금 X%였던 사람의 최종 %」 선(평균 + 고른 시즌, 시작 6시간 뒤부터)과 표.
     기본으로 가장 센 시즌·가장 약한 시즌·이번 시즌(추정이 있으면, 없으면 가장 최근 시즌)을 고른다. 색은 dataviz 기본 범주색 1~3(모든 쌍 검사 통과)을 고른 시즌에 붙인다.
     진행 중 시즌은 컷 예측이 세기를 고쳤을 때만 「S{n}*」(추정, 80% 구간 세로 선)으로 싣는다 — 한섭 12시간~끝의 P_F·m ÷ P_dev 기하 평균으로 같은 잣대(23시즌 곡선)에 옮긴 값 (`site.sink`).
     시즌마다 모양까지 다른 곡선(초반에 더 밀린 시즌 vs 막판에 더 밀린 시즌)은 이 그림으로 알 수 없다고 화면에 쓴다 — 시즌별로 따로 맞추는 것은 하지 않았다 (사용자에게 설명함, 2026-10-18).
   - **실제 관측 점** (2026-10-18 사용자 결정 — 옛 계산기의 지난 시즌 겹쳐 보기를 합침): 고른 지난 시즌(막대사탕으로 고름, 시즌 버튼 22개는 없앰)마다 그 시즌 색으로,
     진행 중 순위 화면의 % 하나에 같은 점수의 최종 %를 끝난 뒤 점수표 곡선에서 붙인 칸(그 사람의 최종 순위가 아님, 사람·일차마다 하나) 가운데
     그때 %가 「지금 X%」의 ÷1.3~×1.3인 것을, 배율(최종 ÷ 그때)은 그대로 두고 「그때 딱 X%였다면 최종 %」(X × 최종 ÷ 그때)에 찍는다. 시작 6시간 뒤부터.
     점이 그 시즌 선보다 위에 많으면 그 시점에 선보다 더 밀린 것이다. 풍선에 원래 그때 %·최종 %·배율, 아래 문장에 시즌별 점 수.
     자료는 `site.sink()`의 `obs`(viz 정답 표 시즌의 관측 칸 모두, 숫자만 — 한섭 2,920 · 일섭 382 · 글섭 37개, 2026-10-18)·`dev`(23시즌 곡선)·`start`·`borrow`다.
     예전 `conv`의 `obs`·`dev`·`levels`·`start`는 여기로 옮기거나 지웠다 (계산기는 이번 시즌 곡선만 씀). 같은 날 `x0 = 1%` 한섭 S29 4 · S38 27 · S41 21개.

7. **방법** (「방법」 탭 `#method`, 2026-10-18 사용자 결정). 위 1~6의 화면 설명을 모은 탭이다. 글은 `site_template.html`에 HTML로 두고, 자료에 따라 바뀌는 값만
   `drawMethod()`가 채운다(예측 방법 이름·도중에 바뀐 방법, 학습 시즌, 계산기 곡선과 이번 시즌 세기, `CONV_RULE` 기준과 세 서버 점검 표, 되돌려 보기 시즌·횟수, 침수 비교 시즌 수, 분석 시즌).
   맨 위 목차 다음 카드 다섯:
   - **작업 흐름** — 모으기 → 읽기(Claude Haiku) → 정리 → 예측 → 공개(GitHub Actions) 다섯 상자(폭 860px 아래에서는 세로). 상자마다 공개 레포의 해당 폴더·파일 링크 하나만 단다
     (사용자 결정 — 「단계별 지도, 단 너무 디테일은 빼고」. 따로 「공개 코드」 탭은 만들지 않았다 — 코드를 보는 사람은 공개 레포로 간다).
     「공개」 상자에는 비공개 레포 이야기를 쓰지 않는다 (2026-10-18 사용자 결정 — 「숫자만 골라 공개 레포와 이 웹에 올립니다」).
     6시간 예약 작업 → 시즌 전용 Sonnet 세션 → 판독만 Haiku라는 역할 나눔, 끝난 뒤 +4일 수집, 「공개 범위」(공개하는 것·않는 것과 까닭, 수집 원칙).
   - **컷 예측** — 지금 방법, 지금 %를 최종 %로 옮기기(침수), 최종 %에서 컷 점수로, 모델 F 설정, 80% 구간, 서버, 신뢰도 표(`predict.GRADE_RULE`을 화면 말로)와 참고값, 갱신.
   - **계산기** — 두 계산기의 원리와 주의, 실선과 점선(위 2의 기준과 표).
   - **지난 시즌 탭** — 위 3~6의 읽는 법 (`m-cut`·`m-rec`·`m-back`·`m-sink`).
   - **검증과 한계** — 개발 검증과 독립 검증, 표본 치우침, 「실제 컷」도 커뮤니티 값이라는 것, 분석 시즌과 분석 페이지 링크.
   - 분석 페이지(`analysis.html`)는 합치지 않았다 (2026-10-18, 사용자가 「통합도 검토」를 맡김). 그 페이지의 ①·②는 모델 F가 아닌 23시즌 평균 곡선·시즌 하나씩 빼기라
     지금 방법을 설명하는 방법 탭에 넣으면 어느 방법이 쓰이는지 헷갈리고, ①은 계산기·침수 비교와, ②는 되돌려 보기와 겹친다. 탭 막대에서 빼고 방법 탭 끝에 「방법을 고르기 전의 분석 화면」으로 링크만 둔다.

- 「읽는 법」 상자는 지웠다 (2026-10-16 사용자 결정 — 내용이 표 아래 메모·등급 안내·맨 위 기준 시각과 겹침). 분석 페이지 링크는 「최종 컷 예측」 소개 문장 끝으로 옮겼다
  (2026-10-18부터 그 자리는 「같은 방법으로 지난 시즌을 되돌려 본 정확도는 「지난 시즌」 탭」 — 분석 페이지 링크는 탭 막대 오른쪽 끝에만).

## 처음 설정 (사용자가 한 번 함)

1. **토큰:** GitHub → Settings → Developer settings → Fine-grained tokens → Generate new token.
   - Repository access: Only select repositories → `jgaram/nikke-soloraid-cutoff`
   - Permissions: Contents → Read and write
   - 만료일은 원하는 대로 정한다. 만료되면 복사가 빨갛게 뜨므로 새로 만들어 바꾼다.

   이름은 `PUBLIC_REPO_TOKEN`, 값은 1번의 토큰이다. 없는 동안 `publish.yml`은 아무것도 하지 않고 초록으로 끝난다.
3. **Pages:** nikke-soloraid-cutoff → Settings → Pages → Build and deployment → Source: Deploy from a branch → `gh-pages` / `/ (root)`.
4. 처음 한 번은 Actions → publish → Run workflow로 돌린다. 그다음부터는 push마다 돈다.
