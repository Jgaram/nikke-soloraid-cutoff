## 왜

S41 재수집은 니마갤 한 시즌을 모으는 데 누적 입력 약 5.5억 토큰을 썼다.
조율 세션이 5시간 사용 한도를 넘겼고, 컨텍스트는 67만까지 컸다.

| 역할 | 누적 입력 | 비중 | 이번 계획에서 |
|---|---:|---:|---|
| 조율 세션 (Opus) | 2.61억 | 47% | 단계별로 세션을 나눈다. 사진을 열지 않는다. 에이전트 수 자체를 줄인다 |
| 판독 (850px 사본) | 1.37억 | 25% | 덱별 피해량을 빼고, 코드 판독을 먼저 한다 |
| 원본 재판독 | 1.26억 | 23% | 기본으로 하지 않는다 (점수 0.1억 단위면 충분) |
| 썸네일 선별 | 0.26억 | 5% | 코드 선별로 바꿀 수 있는지 잰다 |
| 글 텍스트 | 0.03억 | 1% | 코드 추출을 먼저 하고, 모델은 분류만 맡긴다 |

## 정해진 것 (사용자 결정, 2026-10-15)

- **비용 목표:** 모델 비용을 가능한 한 0에 가깝게 한다. 조사 결과에 따라 타협할 수 있다.
- **점수 정밀도:** 0.1억 단위면 충분하다. 보이는 글자 그대로(`*_txt`)는 남기지만, 11자리를 맞추려고 원본을 다시 읽지 않는다.
- **%만 있는 관측도 정식 관측이다.**
  - 제목·본문·사진에서 점수 없이 %만 있어도 모은다.
  - 한 글에 시각별로 여러 %를 적었으면("13시 1.57% 14시 1.59% 15시 1.61%") 시각마다 한 줄씩 남긴다. 하나로 줄이지 않는다.
  - 댓글은 이번 범위가 아니다 (사용자가 고르지 않음).
- **덱별 피해량은 모으지 않는다** (앞서 정함).
- 서버는 원문에 명시된 것만 적는다. 랭킹 화면의 상위 7명 점수(`top7`)는 나중에 분류할 때 쓰도록 남긴다 (앞서 정함).
  분류는 합치기 뒤 따로 도는 [`tools/server_classify.py`](tools/server_classify.py)가 한다 (2026-10-16, [설명](../../docs/solo-raid-cutoff.md#서버-분류-2026-10-16)).

### 4단계 방향 (사용자 결정, 2026-10-15 저녁)

- **정확도를 먼저 본다.** 비용 목표는 그다음이다. 판독 모델은 그대로 Haiku다 (세션 D 근거: 원본 기준 오류 0.31%, 혼합 방식은 오류를 줄이지 못함).
- **외부 트래커·외부 사이트의 순위 화면도 모은다.** 관측 줄에 `src: "tracker"`를 붙여 나중에 빼고 계산할 수 있게 한다.
- **지난 시즌·다른 레이드의 같은 모양 화면은 두 겹으로 거른다.** 코드(글 시각·첨부 이름 날짜·점수 범위)로 먼저 거르고, 애매한 것만 글 문맥으로 가른다.
  문맥을 볼 모델은 시범으로 정확도를 재고 정한다.
- **순위 목록 화면(`rank_list`)은 모두 원본 첨부를 폭 1400px로 읽는다.** 띠 칸도 포함한다.
  세션 E에서 원본은 109/109였고, 남은 Haiku 오류 2줄은 모두 850px 띠 칸 목록이었다.
- ~~**대상은 당분간 니마갤만이다.**~~ → **바뀜:** S40 이하부터 디시·네이버·블라블라링크를 묶어 돌린다 (사용자 결정, 2026-10-15, 「네이버·블라블라링크 붙이기」).
  니마갤은 자기 이름 UA로도 받아지고 robots.txt도 허용한다 → 사람 없이 도는 자동 실행이 가능하다 ([community-access](../../docs/community-access.md#사이트별-robotstxt와-user-agent)).
- **자동 실행을 염두에 두고 만든다.** 시즌 중에 "첫날치만 먼저" 같은 실행이 되도록 기간 단위로 돌리고, 실행 사이 상태를 이어 간다.
  자동 실행을 실제로 켜는 것(UA 전환·Workflow 상시 허락·결과 보관 위치)은 F2 결과를 보고 정한다.

- **effort를 medium으로 잡은 이유:** 무엇을 잴지와 통과 기준을 이 문서에 미리 정해 두었다. 그래서 세션 안의 일은 대부분 코드 작성과 측정이다.
  비용의 대부분은 컨텍스트 누적이다. effort가 높으면 턴마다 생각이 길어지고 탐색 호출이 늘어 누적이 커진다.
  파서 정확도가 막히면 effort를 올리지 말고, 멈춤 규칙대로 결과를 적고 끝낸다.
- A와 B를 동시에 돌려도 되지만 5시간 사용 한도를 같이 쓴다. 하나씩 하는 편이 한도를 관리하기 쉽다.

## 단계

각 단계는 **물어볼 것 → 방법 → 잴 것 → 다음 단계로 가는 기준** 순서다.
통과 기준 숫자는 제안값이다. 결과를 보고 사용자와 다시 정한다.

### 0단계 — 있는 자료로 계산만 (모델 0, 요청 0)

1·2·4번은 세션 A, 3번은 세션 B가 한다.

1. **원본 재판독이 필요한가.** `reads_first` ↔ `reads_orig`를 같은 사진·같은 줄끼리 맞댄다.
   덱별 결과 화면은 빼고 `my_rank`·`rank_list`·`season_end`만 본다.
   - 잴 것: 점수 차이가 0.1억 이상인 줄의 수와 비율, 몇째 자리가 틀렸는지 분포, %·순위 불일치 수
   - 기준: 0.1억 이상 차이가 순위·% 화면 점수 줄의 0.5% 이하이면 원본 재판독을 파이프라인에서 뺀다.
     넘으면 판독자가 `need_orig`를 켠 사진만 원본으로 읽는다.
2. **덱별 피해량을 빼면 얼마나 줄어드나.** `tri` × `kind` 교차표로 지난번 선별 기준에서 덱별 피해량을 N으로 돌렸을 때 판독량을 계산한다.
3. **%만 있는 관측이 얼마나 되나.** 사진의 점수 없는 % 줄, 글 주장의 점수 없는 % 주장을 센다.
   한 글에 %가 둘 이상인 글을 코드로 찾아, 지난번에 하나로 줄인 글 목록을 만든다 (3단계 정답 보강용).
4. **평가 세트를 고정한다** → `data/evalset.jsonl`. 사진 id, 묶음, 정답 줄을 담는다.
   - 양성: `kind == "key"` 667장 전부
   - 음성: 덱별 피해량 200장, 모의전·계산기 화면 사진 최대 200장(줄이 모두 `mock`인 사진 281장 중에서), 그 밖의 자료 155장, 자료 없음 100장
   - 잘라 낸 막대: `skip == "small"`이면서 막대 모양인 286장. 정답이 없다. 기준점 비교의 28행만 정답이 있다 → 2단계에서 정답을 만든다.

### 1단계 — 코드로 사진 읽기 (모델 0)

물어볼 것: OCR과 규칙만으로 순위·%·점수와 화면 종류를 얼마나 맞게 읽나. 모델에 넘겨야 할 사진은 몇 장인가.

1. **준비 (시간 상한 30분).**
   - 세션 임시 폴더 venv에 `rapidocr-onnxruntime`을 설치한다 (1.2.3, pip로 받아지는 것을 2026-10-15 확인).
   - 기본 모델은 중국어·영어라 숫자·`%`·`,`는 읽지만 한글은 못 읽을 수 있다. 한국어 인식 모델(PaddleOCR korean rec의 ONNX)을 받을 수 있는지 먼저 확인한다.
   - 못 받으면 숫자만 읽고, 화면 종류는 배치·색 규칙으로 가르거나 모델에 넘긴다.
2. **사진 받기.** 평가 세트 사진 약 1,600장을 백그라운드로 받는다 (850px 사본, `sha1` 확인, 약 35분). 사진은 세션 임시 폴더에만 둔다.
3. **OCR 원시 결과 저장.** 사진마다 글자·상자·신뢰도를 JSONL로 쓴다. 장당 CPU 시간도 잰다 (4코어).
4. **규칙 파서.**
   - %: `\d{1,2}\.\d{2}\s*%` (일섭 `上位`, 영문 `TOP` 표기도 확인)
   - 점수: 콤마 11~12자리 → 정수
   - 순위·점수·%를 같은 줄(세로 위치)끼리 묶는다. 내 줄과 상위 7명 줄을 구분한다.
   - 화면 종류: 솔로레이드 순위, 덱별 결과, 모의전 탭, 딜 계산기, 협동작전(점수 20억대), 다른 레이드. 갱신 타이머 `갱신 시간 N시간 M분 남음`도 읽을 수 있으면 읽는다.
   - 파서가 스스로 자신 있음/없음을 낸다. %·점수 형식이 맞고, 화면 종류가 정해지고, OCR 신뢰도가 기준 이상이어야 자신 있음이다.
5. **잴 것** (평가 세트 정답과 맞대기)
   - 양성 중 자신 있음 비율(커버리지)
   - 자신 있음 줄의 % 정확 일치율, 점수 0.1억 이내 일치율, 순위 일치율
   - 음성을 S41 순위·% 줄로 잘못 낸 비율. 특히 모의전·계산기
   - 코드 선별 재현율: 양성 사진 중 OCR이 % 또는 9자리 이상 숫자를 하나라도 찾은 비율. 이것이 99% 이상이면 썸네일 선별(모델)을 없앨 수 있다.
6. **다음으로 가는 기준 (제안)**
   - 커버리지 70% 이상, 자신 있음 줄의 % 일치 99% 이상, 점수 0.1억 이내 99% 이상, 음성 오판 1% 이하 → 코드 판독을 기본으로 쓰고, 자신 없는 사진만 2단계로 넘긴다.
   - 커버리지 30% 미만이거나 오판을 줄일 수 없으면 → 코드는 선별과 숫자 칸 자르기에만 쓰고, 판독은 2단계 타일 판독으로 한다.
   - 파서 고치기는 3번까지만 한다. 평가 세트에 맞춰 규칙을 과하게 붙이지 않는다. 마지막에 홀드아웃(평가 세트에서 떼어 둔 20%)으로 한 번 잰다.

### 2단계 — 코드가 못 읽은 것만 모델로

물어볼 것: 모델이 꼭 필요한 사진을 장당 얼마에 읽을 수 있나. Haiku로 되나.

1. **타일 판독.** 사진 한 장씩 여는 대신, 코드가 숫자 칸(내 줄·상위 7명 줄)을 잘라 여러 장을 이미지 하나에 모은다. 칸마다 사진 id 라벨을 붙인다.
   - 지난번에는 사진 1장을 열 때마다 턴이 늘어 누적 입력이 장당 5.6만이었다. 한 번에 여러 장을 읽으면 이것이 준다.
   - 잘라 낸 막대 286장이 첫 대상이다. 정답이 없으니 코드 판독과 모델 판독이 같으면 정답으로 삼는다. 다르면 그 사진만 원본으로 확인한다.
2. **통째 판독.** OCR이 아무것도 못 찾았는데 자료일 수 있는 사진(폰 카메라 사진, 기울어진 사진)은 축소한 사진 4장을 한 이미지에 모아 읽는다.
3. **모델 비교.** 같은 타일을 Haiku와 Sonnet으로 읽어 평가 세트 정답과 맞댄다.
   - 에이전트 정의를 새로 만들지 않는다. 세션 도중에 만든 정의는 쓸 수 없었다.
   - `Agent(subagent_type="raid-vision", model="haiku")`처럼 모델만 바꾼다. (2026-10-15부터 기본 모델이 Haiku다.)
4. **썸네일 선별을 남겨야 할 때** (1단계 코드 선별 재현율이 99% 미만)
   - 지시에 "덱별 피해량만 있는 화면은 N"을 넣는다.
   - Haiku 선별 결과를 지난번 `tri` 및 평가 세트와 맞댄다.
5. **잴 것:** 장당 누적 입력 토큰, 정확도(1단계와 같은 지표), 에이전트 수.
   먼저 30장으로 시범을 돌려 장당 비용을 재고, 전체 비용을 추산해 사용자에게 보인 뒤 늘린다.

### 3단계 — 글 텍스트 (모델 0 목표)

물어볼 것: 제목·본문의 숫자 주장을 코드로 뽑을 수 있나. 모델은 분류에만 쓰면 되나.

1. **코드 추출.** 제목과 본문 앞 500자에서 `(시각 표현, %, 점수 억)` 묶음을 뽑는다.
   - 시각 표현이 여러 개면 묶음을 여러 개 낸다 (`13시`·`지금`·`현재`·`아침`·`어제` 등).
   - %·퍼 없이 소수만 있는 제목("0.7딱코")도 잡는다.
2. **분류.** 자기 기록·예상·질문·커트 전언·지난 시즌을 나눈다. 규칙으로 먼저 해 보고, 안 되는 것만 Haiku에 줄 단위 묶음(200줄)으로 맡긴다.
   질문형 자기 값("지금 4퍼면 20퍼 안에 드냐?")은 자기 기록으로 세고 질문 표시를 따로 붙인다.
3. **잴 것:** `claims_text.jsonl` 대비 재현율·정밀도, 기준점 글 출처 행(제목 64·본문 22) 재현율, 0단계 3번에서 찾은 "여러 값을 하나로 줄인 글"의 복원 여부.
   `posts_min`은 본문 300자뿐이니, 그 안에 있는 주장만 비교한다.

### 4단계 — 합쳐서 한 시즌 다시 돌리기

물어볼 것: 1~3단계 조합을 기간 단위로 돌려 한 시즌을 모으면, 지난 재수집보다 정확하고 싸게 모이나. 나눠 돌려도 한 번에 돌린 것과 같나.

- **대상:** S41 니마갤 (목록 09-24 11:00 ~ 10-04 23:59). 지난 재수집과 맞대 잴 수 있어서 S41로 한다.
  목록·본문·사진은 다시 받는다 (레포에는 `cand.tsv`·`posts_min`·`images.jsonl`만 있다). 지난번 요청은 13,569번, 약 6.5시간이었다.
- **순서 (기간 한 번):** 목록(`list_crawl.py START END`) → 후보(`select_cand.py`) → 본문·사진(`collect.py`) → OCR·파싱·화면 종류(`pipeline.sh`)
  → 시트(`tile_sheets.py`) → Haiku 판독(`raid-tile-read` Workflow) → 목록 화면 원본 판독(같은 Workflow, 원본 시트)
  → 글 숫자 추출(`text_extract.py`) → 애매한 글 분류(Haiku) → 합치기·시즌 거르기.
- **지난번에 남긴 수집 규칙 문제를 고친다.**
  - 작은 사진 규칙: 막대 모양 `max(w,h) ≥ 250 and h ≥ 40`은 살린다.
  - 소수만 있는 제목을 후보로 잡는다.
  - 첨부 이름 날짜가 시즌 전이면 제외한다(`file_date_out`).
  - 한 글의 시각별 여러 값을 시각마다 남긴다.
- **잴 것**
  - 지난 재수집 핵심 줄 2,023줄과 글 주장 1,739개 대비 재현율. 값이 다른 줄은 원본으로 확인해 어느 쪽이 맞는지 센다.
  - 이번에만 있는 줄 (지난번에 판독하지 않은 사진 3,735장에서 나온 것 등)과 그 표본 확인
  - %만 있는 관측 수, 외부 트래커 줄 수, 시즌 거르기로 빠진 줄 수
  - 두 구간으로 나눠 돌린 결과가 한 번에 돌린 것과 같은지 (아래 F2)
  - 비용: 조율·에이전트 각각의 누적 입력, 최대 컨텍스트, 에이전트 수, 걸린 시간, 사이트 요청 수

### 세션 F1 — 4단계 도구

시작할 때: `experiments/2026-10-15-solo-raid-low-cost/README.md의 세션 F1을 실행해`

- **한다**
  1. **UA 옵션.** `dcnet.py`가 환경 변수 `DCNET_UA`를 받게 한다. 기본은 지금처럼 `Claude-User`(사람이 시킬 때).
     자동 실행용은 `nikke-community-research/0.1 (+https://github.com/jgaram/nikke-community)`. 이 UA로 robots.txt와 목록·본문·사진·원본 첨부를 몇 번만 다시 확인한다.
  2. **기간 실행 스크립트** `tools/run_window.sh STATE START END`. 위 순서의 코드 단계(목록 ~ 시트, 글 숫자 추출)를 한 프로세스로 돌리고 `DONE`·`FAILED`만 남긴다.
     조율은 "스크립트 → Workflow → 합치기" 세 번으로 끝나야 한다.
     - **상태(`STATE/`):** 받은 글 번호, 사진 `sha1`, 판독한 칸·사진, 실행 기록. 다음 실행은 이미 한 것을 건너뛴다.
       같은 사진(`sha1`)이 다른 날 다시 올라와도 다시 읽지 않고 새 글에 붙인다.
     - **기간 경계:** 앞 실행의 END보다 1시간 앞에서 겹쳐 시작하고, 이미 받은 글은 건너뛴다. 시즌 중 자동 실행이면 END는 지금보다 30분 전까지로 한다 (막 올라온 글은 사진이 늦게 붙기도 한다).
     - 기존 S41 도구(`list_crawl.py`·`select_cand.py`·`collect.py`)를 이 폴더 `tools/`로 가져와 고친다. 이전 실험 폴더는 고치지 않는다.
  3. **목록 화면은 원본으로.** `rank_list`로 정해진 사진(코드 판정이든 Haiku 1차든)은 원본 첨부를 받아(`orig_fetch.py`, Referer 필요) 폭 1400px로 읽는다.
     코드가 자신 있게 읽은 목록 사진도 원본 판독과 맞대 둘 중 하나만 남긴다 (다르면 원본 판독).
  4. **외부 트래커 칸.** `tile_prompt.md`의 `screen`에 `tracker`(게임 밖 사이트의 순위·점수 표)를 더하고 그 줄도 적게 한다.
     세션 E에서 빠진 key 7장(정답 33줄)으로 시범을 돌려 잰다.
  5. **시즌 거르기 `tools/season_filter.py`.**
     - 코드: 글 시각이 기간 밖, 첨부 이름 날짜가 시즌 전(`file_date_out`), 점수가 같은 기간 관측 분포에서 크게 벗어남 → 뺀다. 애매하면 `unsure`.
     - 문맥: `unsure`만 글 제목·본문 앞 500자와 함께 모델에 묻는다. Haiku로 먼저 시범하고, 부족하면 Sonnet과 비교해 정한다.
     - 잴 것: 세션 D·E의 「그 밖의 자료」 음성 98장, 지난번 `file_date_out` 43줄, 정답 key 줄을 잘못 빼는 수.
  6. **합치기 `tools/merge_obs.py`.** 사진 판독(코드·Haiku·원본)과 글 주장을 S41 재수집 `obs_images`·`claims_text`와 같은 칸으로 펼친다. `src`(code·haiku·orig·text·tracker)를 남긴다.
  7. **작은 구간 시험.** S41 첫 3시간(09-24 11:00~14:00)을 자기 UA로 처음부터 끝까지 돌린다. Workflow는 사용자가 그 세션에서 허락할 때만 쓴다.
- **하지 않는다:** S41 전체 실행, 다른 커뮤니티.
- **멈춤 규칙:** 도구 고치기는 단계마다 3번까지. 시험 구간 실행은 반복 구간이라 컨텍스트 15만 멈춤을 쓴다.
- **남길 것:** 코드는 `tools/`, 시험 결과 지표는 `data/stage4/`. 「결과 — 세션 F1」에 도구 사용법·시험 결과·F2 예상 요청 수와 비용을 쓴다.

## 조율 세션 운용 규칙 (모든 단계)

지난번 조율 비용의 원인은 긴 세션, 에이전트 완료 알림 165개, 조율자가 직접 연 사진, 긴 도구 출력이었다.

- **조율자는 사진을 열지 않는다.** 확인이 필요하면 코드 통계나 하위 에이전트 한 줄 요약으로 본다.
- 도구 출력은 20줄 안팎으로 줄인다. 긴 결과는 파일에 쓰고 요약 숫자만 본다.
- 수집·다운로드·OCR은 백그라운드 스크립트 하나로 돌린다. 끝나면 요약 한 줄만 본다. 진행 중에 자주 들여다보지 않는다.
- 에이전트는 타일로 묶어 수를 줄인다. 에이전트 하나에 배치 하나, 결과는 파일, 답은 한 줄로 받는다.
- Workflow 도구로 배치 전체를 돌리면 조율자에게 알림이 하나만 온다. ~~사용자가 그 세션에서 명시적으로 허락했을 때만 쓴다.~~ → **Haiku 기반 Workflow는 상시 허락** (사용자 결정, 2026-10-15, AGENTS.md). 다른 모델이 조금 섞이는 것은 괜찮다.
- **세션은 「세션 나누기와 effort」대로 나눈다.** 세션이 끝나면 결과 파일과 이 README의 「결과」를 갱신하고 커밋한다. 다음 세션은 README만 읽고 시작한다.
- **컨텍스트 15만 멈춤은 반복 실행 구간에만 쓴다** (2026-10-15 사용자 결정). 반복 실행은 배치 판독·다운로드·재수집처럼 같은 일을 되풀이하며 턴이 쌓이는 구간이다.
  넘으면 그 자리에서 정리·커밋하고 세션을 끝낸다. 남은 일은 README에 적는다.

## 위험과 열린 질문

- **화면 종류 판별이 가장 어렵다.** 지난번 관측의 14%가 모의전 탭·딜 계산기였다. 한국어 OCR이 안 되면 코드로 가르기 어렵다.
- 폰 카메라로 찍은 사진, 기울거나 편집한 사진, 일·영문 UI는 OCR이 약할 수 있다.
- 평가 세트 정답의 대부분은 Sonnet 판독이다. 사람이 검수한 정답이 아니다. 코드와 정답이 다르면 정답이 틀렸을 수도 있다. 다른 사진은 원본으로 확인한다.
- 코드 선별로 썸네일 선별을 없애면, OCR이 글자를 못 찾는 자료 사진을 놓친다. 1단계에서 재현율을 재기 전까지는 없애지 않는다.
- 사이트 요청 시간은 모델 비용과 별개다 (지난번 13,569번, 약 6.5시간). 이번 계획은 토큰만 줄인다.
- 다른 커뮤니티(네이버·아카·블라블라)는 이번 범위 밖이다.
- **키워드 없는 사진 글의 누락.** 후보 규칙(A·B·E) 밖의 사진 글에 자료 글이 약 330건(순위·% 자료 약 70건) 남는다는 표본 추정이 있다 (S41 재수집 「후보 규칙과 누락 점검」).
  OCR은 CPU라 모델 비용 없이 사진 글 전부를 훑을 수 있지만, 사이트 요청이 두 배 넘게 는다. 정확도 우선이므로 F2 뒤에 요청 수와 함께 따져 정한다.
